# 外部仕様書

[English](external-spec.md)

外部仕様。

## 1. プロダクト概要

複数デバイスで同じ RSS 購読体験を提供する、軽量でシンプルな RSS リーダー。

- シンプル・スタイリッシュ・高速な UI/UX
- ローカルファースト（アカウント不要、データは手元に）
- クラウドストレージ（Dropbox / Google Drive / OneDrive）経由でのデバイス間同期

## 2. 対応プラットフォーム

| プラットフォーム | 対応 |
| --- | --- |
| Windows / macOS / Linux | ✅ Compose Multiplatform（現行） |
| Android | ✅（Compose Multiplatform、現行。クラウド同期は Dropbox / OneDrive に対応。Google Play 開発者サービスがインストール済みかつ有効かつ最新の端末では Google Drive も利用可能。§4 および [sync-architecture.ja.md](sync-architecture.ja.md) 参照） |
| iOS / iPadOS | 予定（最初は Compose、その後 SwiftUI ネイティブ UI） |
| macOS（ネイティブ） | 予定 — 上記の Compose 版とは別に、ネイティブ SwiftUI 版 macOS アプリを提供予定 |

## 3. 対応フォーマット

RSS 2.0 / Atom 1.0（RSS 1.0/RDF も緩く解釈）。JSON Feed は α 以降。

## 4. 同期方式

- Keryx へのアカウント登録なし。ユーザー自身のクラウドストレージ（Dropbox / Google Drive / OneDrive）を同期バスとして
  利用する。有効な接続は常に 1 つで、どのプロバイダーを使うかはユーザーが選択・切替する（同時接続はしない）。
- 同期ファイルは `keryx.db` の `VACUUM INTO` スナップショットを gzip 圧縮したもの（ローカル専用の
  `articles_fts` 検索索引・4 つの `idx_articles_*` インデックス・`sync_state` テーブルを除く）——
  [sync-architecture.ja.md](sync-architecture.ja.md) 参照。
- 同期対象: 購読リスト・フォルダー・既読状態・スター・タグ構造・記事本文・グローバル設定。
- 非同期対象: デバイスローカル設定・クラウド認証情報。
- インポート / エクスポートは OPML。
- 同期の実行中は、設定画面のクラウド同期タブで接続中プロバイダーの行に単なるスピナーではなく現在の進行状況
  （クラウドを確認中・ダウンロード中・データを統合中・検索インデックスを更新中・アップロードを準備中・
  アップロード中・クラウドデータを退避中）を表示するため、時間のかかる初回同期でも止まっているように見えない —
  [sync-architecture.ja.md](sync-architecture.ja.md) 参照。
- **OneDrive が対応するのは個人用 Microsoft アカウントのみ** — 職場・学校（Microsoft 365 / Entra ID）
  アカウントは連携できない。Keryx は同期ファイルを OneDrive のアプリ専用の隠しフォルダーに置くが、
  そのフォルダーだけにアクセスを限定する Graph 権限は個人用アカウントにしか提供されておらず、
  組織アカウントに対応するにはユーザーのドライブ全体へのアクセスを要求することになるため。
  [sync-architecture.ja.md](sync-architecture.ja.md) の「クラウド認証」を参照。
- **Android の Google Drive は別経路で、Google Play 開発者サービスがインストール済みかつ有効かつ最新の端末でのみ利用できる。**
  Dropbox と OneDrive はデスクトップと同じ `keryx://oauth2/callback` カスタム URI リダイレクトを使う
  PKCE パブリッククライアントだが、Google の OAuth ポリシーは Android クライアント種別に対して
  カスタム URI スキームとループバックの両方を廃止しているため、デスクトップ向け構成
  （ループバックリダイレクト + `client_secret` を使う「デスクトップアプリ」クライアント）は
  Android には流用できない。代わりに Google 自身が推奨する Play 開発者サービスの
  `AuthorizationClient` を使う — クライアントシークレットもバックエンドサーバも不要。
  Play 開発者サービスが無い（脱 Google の ROM）・無効化されている・認可リクエストを処理するには
  古すぎる端末では Google Drive を選択肢として出さないが、
  Dropbox・OneDrive・ローカルのみは従来どおり利用できる。アカウントも同期ファイルもデスクトップ版と
  共通。詳細は [sync-architecture.ja.md](sync-architecture.ja.md) の「Android での Google Drive」を参照。

## 5. 競合解決ポリシー

| データ | ポリシー |
| --- | --- |
| 既読・未読、スター | タイムスタンプ後勝ち（`read_at` / `starred_at`） |
| 記事本文 | OR マージ（どちらかにあれば保持） |
| 購読リスト（追加） | OR マージ |
| 購読リスト（削除）、タグ・フォルダー、グローバル設定 | タイムスタンプ後勝ち（論理削除で伝播） |
| デバイスローカル設定 | 同期しない |

詳細は [sync-architecture.ja.md](sync-architecture.ja.md)。

## 6. セットアップフロー

初回起動でローカルのみ / クラウド同期（Dropbox・Google Drive・OneDrive。Android では Google Drive は
Google Play 開発者サービスがインストール済みかつ有効かつ最新の端末でのみ表示される、§4 参照）を選択する。クラウド選択時は OAuth 認証後、クラウドに既存データがあれば初回同期で自動的に
マージ（インポート）される。

## 7. 基本機能

- URL 指定でのフィード購読、タグによる分類、OPML インポート/エクスポート。`.opml` ファイルは
  他アプリから直接開くことでもインポートできる — デスクトップではファイル関連付けによる
  ダブルクリック、Android ではファイルマネージャやメール添付からの「Keryx で開く」
- フィードが1件も購読されていない間は、記事一覧に通常の「記事がありません」の代わりに
  「フィードを追加」ボタン付きの空状態メッセージを表示する。Android の狭い幅では、
  フィード一覧自身の「+」ボタンを持つナビゲーションドロワーがこの場面で自動的に開くことがある
  （正確な条件は §9「それより狭い幅」参照）ため、ユーザー自身がドロワーを探さなくても
  ボタンに届くようにしている
- フィード健全性管理: 301/308 は購読 URL を自動更新（通知）、410 Gone は通知センターに警告、
  連続エラーはフィード一覧にインジケータ表示
- アプリ内アップデート（リリースページへのリンクだけでなく、ダウンロード＋インストールまで）:
  対応するのは macOS の `.app`、Windows の MSI インストールまたは portable ZIP、Linux の
  portable ZIP のみ（deb/rpm インストールや Snap インストール、認識できないインストール形態は
  リリースページを開く従来の挙動にフォールバック）、そして Android のサイドロードインストール（Google Play 経由では
  提供しない——Play が既にアプリ自身を更新してくれるため）。検知した時点から通知センターのベル・
  デスクトップのタスクトレイ・アプリメニューの Help メニューで提示する（後ろ 2 つには同一の項目が
  出る。ここは任意のタイミングで確認を要求する場所でもあり、何も保留がなければ「更新をチェック」
  と表示される）。ダウンロードもインストールも常に個別の明示的な
  ユーザー操作であり、サイレントに／自動でインストールされることはない。ダウンロードしたファイルは
  インストール前に GitHub リリース自身の SHA-256 ダイジェストと照合して検証する。設計の詳細は
  [background-update.ja.md](background-update.ja.md)、この検証が保証すること／しないことは
  [SECURITY.ja.md](../SECURITY.ja.md) を参照。
- 記事一覧・記事ビュー（リーダービュー）。**記事を選択した瞬間に既読**。未読に戻す操作あり。
  リーダーをスワイプして記事間を移動する場合（§9 参照）、「選択した瞬間」とはスワイプが記事の上に
  落ち着いた瞬間を指す——リーダーが次に備えて用意している隣の記事は、読み込まれてはいるが選択されて
  おらず、実際にスワイプして到達するまで未読のままである。
- **「未読のみ」は、記事が既読になった瞬間には一覧から外さない**（読み進めている最中に一覧がずれない
  ようにするため、意図的な仕様）——代わりに、記事一覧のツールバーに「既読記事を非表示」という独立した操作が
  あり（「未読のみ」トグルのすぐ隣に配置し、取り違えやすい「すべて既読にする」とは離してある）、
  いつでもその時点の未読のみの状態に一覧を戻せる。隠す対象（選択中の記事以外の既読記事）が無いときは常に表示されたまま無効になり、
  実行しても「未読のみ」自体がオフになることはない。
- **現在のスクロール位置の外に届いた新着記事は、気づかれないまま静かに積み重なるのではなく、
  フローティングのピル**（例：「新着 12 件」）**として提示される**——タップするとその新着記事へ
  直接ジャンプする。一覧を開いたまま新着が発生するケース（手動更新／バックグラウンド更新、
  pull-to-refresh、あるいは他端末で取得された記事がクラウド同期のマージで入ってくる場合）を
  カバーする。いずれもアプリがフォアグラウンドにある間は OS 通知が出ない経路である。
  ウィンドウ幅・プラットフォームを問わず、フィード一覧の未読バッジがナビゲーションドロワーの
  裏に隠れる Android の 1 ペインレイアウトを含めて常に現れる。一方、**それまで記事が 1 件も
  無かった一覧に初めて記事が入ったとき**（新しく購読したフィード、フィードを割り当てたばかりの
  空のフォルダー／タグ）**には出ない**——見逃しようのあるものが元々無いため。同様に、フィードを
  購読した直後にそのフィードの記事が「新着」として出ることもない——購読した本人の目の前に
  既に表示されているものだからである。
- スター（永続）、外部ブラウザーで開く
- SQLite FTS5（trigram）によるローカル全文検索（2 文字以上 — 3 文字以上は trigram インデックス、2 文字のみからなるクエリは新着順の `LIKE` 走査にフォールバック、3 文字以上を含む混在クエリは FTS5 ランク順を使用。[db-schema.ja.md](db-schema.ja.md) 参照）。検索は現在選択中の購読リストの範囲（すべてのフィード／スター付き／特定のフィード／フォルダ／タグ）を絞り込むものであり、常に全体を検索するわけではない — すべてのフィードを対象に検索したい場合は先に「すべてのフィード」を選ぶ。
- デスクトップ通知・タスクトレイ常駐（閉じるとトレイに収納）・通知センター。
  Linux ではトレイに D-Bus の `org.kde.StatusNotifierItem` + `com.canonical.dbusmenu`、通知に
  `org.freedesktop.Notifications` を使い、StatusNotifierItem ホストが居ない環境では AWT の
  システムトレイにフォールバックする。デスクトップでは未読数を Dock/タスクバー/ウィンドウアイコンに
  直接数字バッジとして合成表示する。Android では新着記事の通知を `NotificationManagerCompat`
  経由で投稿し（Android 13+ では OS の通知権限をリクエスト）、バックグラウンド更新は `WorkManager` で
  設定した間隔に概ね従って実行される。アプリ内の「アップデートを確認」は、サイドロードではなく
  ストア（現状は Google Play のみ）からインストールされた場合には非表示になる — そのストアが既に
  アプリを自動更新するため。Android には数字バッジに相当する仕組みが無い — アクティブな通知と
  独立してアプリアイコンのバッジ数を設定する API がプラットフォームに存在しない（iOS の
  `setApplicationIconBadgeNumber` に相当するものが無い）ため、代わりに OS 自身の通知ドット
  （アクティブな通知の有無に連動）と、対応ランチャーでは長押しで見える件数（`setNumber` 経由）を表示する。これは
  見落としではなく意図的な非対称であり、詳細は `background-update.ja.md` を参照。

### フィード URL 変更・消滅時の挙動

| HTTP | 挙動 |
| --- | --- |
| 301 / 308（恒久） | 購読 URL を自動更新（通知） |
| 302 / 303 / 307（一時） | 追従するが購読 URL は変更しない |
| 410 Gone | 通知センターに警告（自動削除はしない） |
| タイムアウト | 定数回リトライ後にエラー通知 |

## 8. アクセシビリティ・国際化

- UI 文言はすべて Compose Resources（日本語の `values/strings.xml` ——既定かつフォールバック——に加え、
  同じキー集合の英語 `values-en/strings.xml`）で管理。システムロケールに応じて選択し、いずれの言語にも
  該当しなければ日本語へフォールバック。
- 文字サイズ設定（`LocalDensity` の fontScale に反映）。

## 9. UI 方針

**各プラットフォームは、単一の共通デザインシステムではなく、それぞれ自身のネイティブな UI 作法に従う。**
macOS はフラットで SF 寄りの見た目、Android は Material 3 自身のコンポーネント・形状・リップル
フィードバック、iOS は将来的にネイティブ SwiftUI になる。**Windows と Linux は意図的な例外**である —
Java/Swing 自身のプラットフォーム統合機能は両 OS を同程度にネイティブ化するには力不足なため
（後述の Look & Feel・コンテキストメニュー・ファイルダイアログの詳細、および
`known-issues.ja.md` を参照）、両者は独自のネイティブ化を持つ代わりに macOS のフラットな
見た目を共用する。Material 3 はこの原則の Android における具体的な実装である——
本ドキュメントで「Material 3」と書かれている箇所は、特に断りが無い限り Android 固有の記述として
読むこと。Android 自体の配色は、常にアプリ固定のティールパレットとは限らない: Android 12+（API 31+）
ではシステムの壁紙から導出される Material You のダイナミックカラー
（`dynamicLightColorScheme`/`dynamicDarkColorScheme`）を使い、それより古いバージョンでは固定のティール
配色にフォールバックする。ライト/ダーク/システム対応。3ペインレイアウト（フィード一覧・記事一覧・記事詳細）+
キーボードナビゲーション。狭い幅では同時に表示するペイン数を減らして適応する（後述）。

### 幅による適応レイアウトとタッチ入力（Android）

**3ペイン幅（デスクトップの定常状態）。** ウィンドウは3ペインが必要とする幅より狭くはならないため、
常に3ペインすべてを、フィード一覧を常設のサイドバーとして表示する。この「3ペインが必要とする幅」は、
各ペインの最小幅ではなく意図した幅で測る: 3枚を同時に下限へ張り付かせればかろうじて収まる、という
程度の幅——たとえば Android タブレットの縦向き——は狭い側として扱って2ペインを表示し、大型 Android
タブレットの横向きは本当に十分広いので3ペインになる。

**それより狭い幅。** フィード一覧の代わりに Gmail 風のナビゲーションドロワーが現れる——ハンバーガー
ボタンから開くほか、フィードも同期先クラウドアカウントも無い状態でアプリを初めて開いたときは自動的に
開かれ、新規ユーザーが探さなくてもドロワー（と最初のフィードを追加する「+」ボタン）を目にできるように
している。スマートフォン幅の画面では、残る2ペイン（記事一覧・記事詳細）のうち1枚を、それぞれ戻る
操作を持つ階層スタックとして表示する。タブレット幅の画面では両方を常時同時に表示する——リーダーが
自分の戻る操作を失いながら記事一覧側も常設ペインを得ない、という幅は存在しない（後述のスワイプ操作
についての注記を参照）。これら2枚のペイン自体の内容は、この間で変わらない——同時に画面に出るペインの
数だけが変わる——ただし検索だけは例外である。

**検索欄の配置。** 3ペイン幅では検索欄はこれまでどおりフィード一覧のサイドバーにとどまり、結果は
その隣の記事一覧に反応的に表示される。それより狭い幅ではドロワー自体に検索欄は無く、スマートフォン幅・
タブレット幅のどちらも記事一覧自身のヘッダーから検索に入る——どちらの幅でも常に画面に残る唯一の
ペインであり、同じクエリの編集可能な複製を2つ作らずに済む場所だからだ。タップすると検索欄自体が
その結果の直上——通常はハンバーガーボタンが占めているのと同じヘッダー——に移動し、スマートフォン幅と
タブレット幅の間で回転してもその位置にとどまる。

**検索が絞り込む対象。** どの幅でも、検索は独立した行き先ではなく、いま選択されている購読リストの
項目を絞り込むものである。3ペイン幅ではこの選択はその間ずっとサイドバーに表示・ハイライトされたまま
になり、クエリが何に対して照合されているかを常に明示する。それより狭い幅ではフィード一覧はドロワー
であり、検索に辿り着く時点（記事一覧自身のヘッダーから）で通常すでに閉じているため、検索中は選択が
画面に見えていない。いずれの場合も、クエリを消す（狭い幅では展開された検索欄から戻る）と、その同じ
選択の絞り込み前のリストにそのまま戻る。

マウスとタッチスクリーンで異なるアフォーダンスが必要な箇所は、根底の操作自体を変えずに両対応する:
フィード/フォルダーの並べ替えは、マウスでは通常のクリック&ドラッグ、タッチでは専用ハンドルアイコン
からのドラッグになる（タッチでは開始ジェスチャーを区別しないと、行の他の部分を通常どおりスクロール
できなくなるため）——これはドロワーの中でも、元のサイドバーだったときと同じように機能する。
デスクトップの右クリックコンテキストメニューはAndroidでは長押しメニューになる。デスクトップの
アプリケーションメニューから開く設定は、メニューバーを持たないAndroidでは独自の入口を持つ:
フィード一覧・ドロワーの一番下、フォルダー/タグ/フィードのスクロール領域の下に固定されたラベル付きの
行で、ドロワー自身のヘッダーにはその代わりにアプリ名が表示される。設定画面自体もそこでは独自の
戻る矢印を持つ — ほぼ全画面のダイアログのため、それ以外にタップで抜け出す手段がないからだ。
リスト行（フィード・フォルダー・タグ・記事）はAndroidではM3の最小タッチ密度に合わせて背が高くなる。
キーボードナビゲーション（ペイン間の矢印キー、記事間の J/K、選択中のフィード一覧項目への
F2/Delete）はデスクトップ専用ではない: Android タブレットには物理キーボードが接続されうるため、
同じショートカットがそこでも機能し、より狭いレイアウトのフィード一覧ドロワーの中にも届く。
キーボードフォーカスを持つペインの選択行には、キー入力の行き先を示す `secondary` の輪郭線が
付く——Android 自身の M3 選択色はデスクトップの濃淡差と違ってペインフォーカスで変わらないため、
この輪郭線がフォーカス中ペインと非フォーカス中ペインの選択の唯一の見た目の違いになる。この輪郭線は
物理キーが実際に一度押されて以降にしか現れないため、タッチのみのセッションではキーボード
ナビゲーション用のフォーカス表示が出ることは一切ない。検索欄自身にフォーカスがある状態で↓/↑を
押すと、その欄にはキャレット移動としての意味がないため、そのまま検索結果一覧へと降りる——
クエリを入力してから結果を閲覧するまで、間にタップを挟まずキーボードだけで移動できる。

スクロール位置の見せ方はプラットフォームごとに異なり、それぞれ自身の作法に従う——対象は
フィード一覧・記事一覧・セットアップ画面（ダイアログ自身のスクロール領域にはどちらの
プラットフォームでもインジケーターは無い）。デスクトップは各々の脇に常時表示・ドラッグ可能な
スクロールバーを置く。Android は代わりに、
一覧が実際にスクロールしている間だけ現れ、止まってからしばらくしてフェードして消える細い
インジケーターを表示し、意図的にドラッグ**できない**——Android 自身の一覧が、スクロールバーでは
なくコンテンツを直接ドラッグして動かすのと同じオーバーレイの作法である。ナビゲーションバーには
決して重ならない。記事リーダー本文は実ブラウザビューの内部でスクロールしており、そのエンジン
自身の既定のスクロールインジケーター挙動に従う——OS ごとの違いは `app-architecture.md` の
「Article Reader (native WebView)」参照。いずれの場合も OS ではなくアプリ内のライト/ダーク設定に
従い、それは自身が描くスクロールバーやフォームコントロールの配色にも及ぶ——Android ではその
配色は CSS ではなくネイティブ呼び出し経由でスクロールバーに届く。同プラットフォームの WebView は
ページの描画エンジンの外側で自身のスクロールバーを描くため（詳細は `app-architecture.md` 参照）。
**Linux arm64 では**デスクトップ版にネイティブ WebView が一切存在しないため、リーダーは
Compose 描画の簡易表示にフォールバックする（ブロック構造・インライン装飾・画像。本物の
ブラウザエンジンが必要なコンテンツは代わりに外部で開く）——`known-issues.md` 参照。

狭いレイアウト（スマホ幅・タブレット幅の両方）では、記事詳細ペインにもデスクトップには存在しない
タッチ専用のアフォーダンスが加わる: リーダー上の水平スワイプで、一覧と同じ並び順で次/前の記事へ
移動できる。指の動きに追従してスライドし、指を離すとその位置に収まる。ドラッグで現れてくるのは
移動先の記事そのものであり、今の記事があった場所に空白が開くわけではない。一覧の先頭/末尾を越えて
さらにスワイプした場合も本文はわずかに動いてから跳ね返るため、境界に達したことをジェスチャーが
何もしないのではなく体感として伝える。**記事からスワイプで離れてすぐ戻ると、先頭ではなく読んで
いた位置に戻る**——両隣の記事はそのまま保持されているので、離れた記事はそのままの状態で残っている。
この記憶は前後 1 記事ずつが対象で、リーダーが画面に出ている間だけ保たれる: 2 記事以上離れてから
戻った場合、記事一覧に戻った場合、スマホ幅とタブレット幅の間で画面を回転させた場合は、いずれも
また先頭から始まる（後で開き直した場合も同様）。縦方向の移動量が横方向の移動量よりはっきり
小さいとは言えないスワイプはページ送りではなくスクロールとして扱われる（横方向優位の斜め
ドラッグはページ送りとして成立する）。スクロールの直後しばらくはスワイプを受け付けないので、
スクロールのつもりのフリックで記事が変わることはない。この操作は、デスクトップより狭い幅で
リーダーが画面上に存在してさえいれば常に有効である。同じリーダー・同じ一覧順・同じ次/前操作が、
リーダーの隣に戻るボタンがあるかどうかに関わらず適用されるためである。該当するのは次の2ケース:
記事へドリルダウンしたスマホ幅の画面、および自分の戻る操作を持たない記事一覧の常設隣人として
リーダーが表示されるタブレット幅の画面（縦向き、および3ペインに足りる幅を持たないタブレットの
横向き。Gmail 自身のタブレット閲覧ペインと同じ構成）。
大型タブレットの横向きも含むデスクトップ幅の3ペインレイアウトでは
リーダーは常駐する、キーボード操作前提のペインであり（J/K —`app-architecture.md`参照）、
そこではこのスワイプ操作は適用されない。

記事一覧にはもう一つ、デスクトップには存在しないタッチ専用のアフォーダンスがある。Android では
**すべての**幅（大型タブレットが到達する3ペインレイアウトも含む）で有効で、マウスには引っ張る
ジェスチャーがないためデスクトップでは提供しない: **一覧を下に引っ張ると更新される**（Material 3
自身の Pull to refresh インジケーターを使う）。全フィードを更新するツールバーの更新ボタンは
これまで通りだが、引っ張って更新する場合は、いま画面に出ている一覧の元になっているフィードだけを
更新する:

| フィード一覧で選択中の項目 | 引っ張って更新する対象 |
| --- | --- |
| すべてのフィード / スター付き | 全フィード（スター付きの記事はどのフィードにも属しうるため） |
| フィード | そのフィードだけ |
| フォルダー | そのフォルダーに入っているフィード |
| タグ | そのタグが付いているフィード |

選択中の項目が購読中のフィードを一つも含まない場合（中身のないフォルダーやタグ）は、取得も同期も
せずにすぐ終わる。一覧が空でも（例えば「未読のみ」で未読が一件もないとき）引っ張れるが、検索結果の
表示中——検索結果の一覧を引っ張るのは、その裏にあるフィードの更新を求める操作ではない——と、
フィードが一件もないときは無効になる。ツールバーの更新ボタンと同じく、クラウドに接続していれば
更新のあとに同期が続き、インジケーターはフィードの取得だけでなくその同期が終わるまで表示される。
更新や同期がすでに動いている間（バックグラウンド更新など）に引っ張った場合は新たには何も始めず、
動いている処理が終わるまでインジケーターを表示し続ける。ジェスチャーが使える場面では、同じ更新を
ジェスチャー以外からも実行できる: 一覧の TalkBack カスタムアクション（「この一覧を更新」）と、
物理キーボードの Ctrl+Shift+R である。

Compose が描画していない面 — アプリケーションメニューバー・コンテキストメニュー・ダイアログの
ボタン列 — は実際の Swing/AWT ウィジェットなので、プラットフォームの Look & Feel に従う。
macOS と Windows はシステム標準を使い、Linux は Keryx 自身の teal テーマに合わせて配色した
FlatLaf を使う（Java の Linux 向けシステム L&F は GTK2 世代のエミュレーションで、現代の
デスクトップでは古く見えるため）。ライト/ダークはアプリのテーマ設定に再起動なしで追従する。
コンテキストメニューは macOS では `java.awt.PopupMenu`（本物の `NSMenu`）、Windows と Linux では
`javax.swing.JPopupMenu` を使う。Linux は AWT のポップアップが Look & Feel を完全に無視するため、
Windows は JDK の AWT メニューピアが表示スケールを一切考慮せず、100% を超えるとカーソルから離れた
位置に開いたうえラベル同士が重なって描画されるため（`known-issues.md` を参照）。トレイメニューも
同じ分岐に従っており、Windows が Compose の `Tray()` ではなく独自の `WindowsTray` を持つのはこのため。
OPML インポート/エクスポートのファイルダイアログは上記とは異なる分岐で、
macOS **と Windows** は `java.awt.FileDialog`、Linux のみ `javax.swing.JFileChooser` を使う
（AWT 自身のファイルダイアログはアプリをクラッシュさせうる GTK ネイティブコードを経由するため。
`app-architecture.md` と `known-issues.md` を参照）。UI フォントは OS 標準で、macOS は SF Pro、Windows は Segoe UI、
Linux は Look & Feel が解決したフォント、次にデスクトップの設定フォント（XSettings から取得）、
取得できなければ Adwaita Sans / Cantarell / Ubuntu / Noto Sans / DejaVu Sans の順にフォールバックする。

## 10. プライバシー・セキュリティ

- 開発者が運営するサーバーはなく、アカウント登録も不要。Keryx が通信するのは利用中の機能に直接
  関係するサーバーのみ（購読中の各フィードとその favicon、更新チェック/ダウンロード用の
  GitHub、接続している場合のみ Dropbox / Google Drive / OneDrive）で、常に端末から直接行う——
  完全な一覧は [PRIVACY.ja.md](../PRIVACY.ja.md)「アプリが行う通信」を参照。
  Keryx 自身の通信（クラウド同期・更新チェック・
  更新ダウンロード）は常に HTTPS を使用する。購読フィードは、URL が明示的に `http://` である場合
  （またはそこへリダイレクトされる場合）は平文の HTTP で取得される——スキームを指定しない
  フィード URL は HTTPS に補われるが、明示的な `http://` は上書きしない。ただしリーダーは画面に
  出ている記事の両隣をスワイプで移動できるよう用意しておく（§9）ため、それらの本文は——含まれる
  画像や埋め込みコンテンツも含めて——開く前に、開いたときと同じように取得される。それらが既読に
  なることはない。
- 各クラウドプロバイダー（Dropbox・Google Drive・OneDrive）のトークンはそれぞれ独立してプラットフォームの
  セキュアストレージに保存する。desktop: macOS は Keychain（`security` CLI 経由）、Windows/Linux は
  Credential Manager / Secret Service（java-keyring 経由）、Snap 版だけはデスクトップの Secret portal から
  得たアプリ専用の鍵で暗号化されたローカルストア（libsecret 経由。java-keyring は使わない）——利用不可時は
  データディレクトリのファイルにフォールバック。Android: プロバイダーごとに Android Keystore が保持する
  AES-256/GCM 鍵。両方の詳細は `sync-architecture.ja.md`「Token Storage」参照。

## 11. 技術選定

| レイヤー | 採用技術 |
| --- | --- |
| UI | Compose Multiplatform（Android は Material 3、他プラットフォームはプラットフォーム固有 UI — §9 参照） |
| 状態管理 | androidx.lifecycle ViewModel + Koin |
| DB | SQLDelight（SQLite）+ FTS5（生 SQL） |
| HTTP | Ktor client（desktop は CIO、Android は OkHttp） |
| RSS/HTML/XML パース | ksoup |
| シリアライズ / 日時 | kotlinx-serialization / kotlinx-datetime |
| クラウド同期 | Ktor + Dropbox / Google Drive / OneDrive（Microsoft Graph）REST API（OAuth PKCE + リフレッシュトークン） |
| i18n | Compose Resources |
| テスト | kotlin-test + kotlinx-coroutines-test + Ktor MockEngine |
| ビルド | Gradle 9.7.1（Kotlin 2.4.10 / Compose Multiplatform 1.11.1 / JDK 25 toolchain） |
| 画像ロード | Coil3（favicon 表示。SVG デコード対応、既存 HttpClient 共有、ディスクキャッシュあり） |

フィード一覧・記事一覧の両方で、favicon（`feeds.favicon_url`）を Coil3 の `AsyncImage` で表示する。
未取得・読み込み失敗時はレター（頭文字）アバターまたは汎用アイコンにフォールバックする。
