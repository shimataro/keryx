# 外部仕様書

[English](external-spec.md)

外部仕様。

## 1. プロダクト概要

複数デバイスで同じ RSS 購読体験を提供する、軽量でシンプルな RSS リーダー。

- シンプル・スタイリッシュ・高速な UI/UX
- ローカルファースト（アカウント不要、データは手元に）
- クラウドストレージ（Dropbox / OneDrive / Google Drive）経由でのデバイス間同期

## 2. 対応プラットフォーム

| プラットフォーム | 対応 |
| --- | --- |
| Windows / Linux | ✅ Compose Multiplatform（現行） |
| Android | ✅（Compose Multiplatform、現行。クラウド同期は Dropbox / OneDrive に対応。Google Play 開発者サービスがインストール済みかつ有効かつ最新の端末では Google Drive も利用可能。§4 および [sync-architecture.ja.md](sync-architecture.ja.md) 参照。F-Droid 版は Play 開発者サービスを含まないため Google Drive が一切無く、アプリ内アップデートも無い — §4 と §7 参照） |
| iOS / iPadOS | 開発中（SwiftUI ネイティブ UI。ロジックは `:shared` で他プラットフォームと共有し、Compose 版は挟まない。[app-architecture.ja.md](app-architecture.ja.md) の「Apple ネイティブアプリ（SwiftUI）」参照） |
| macOS | ✅ ネイティブ SwiftUI アプリ（現行。Apple Silicon、macOS 14 以降）。ロジックは `:shared` で共有する。Compose 版 macOS ビルドに代わるもので、Compose 版はもうリリースせず内部の確認用としてのみ残す。[app-architecture.ja.md](app-architecture.ja.md) の「Apple ネイティブアプリ（SwiftUI）」参照 |

## 3. 対応フォーマット

RSS 2.0 / Atom 1.0（RSS 1.0/RDF も緩く解釈）。JSON Feed は α 以降。

## 4. 同期方式

- Keryx へのアカウント登録なし。ユーザー自身のクラウドストレージ（Dropbox / OneDrive / Google Drive）を
  同期バスとして利用する。有効な接続は常に 1 つで、どのプロバイダーを使うかはユーザーが選択・切替する
  （同時接続はしない）。
- **OneDrive が対応するのは個人用 Microsoft アカウントのみ** — 職場・学校アカウントは連携できない。
  詳細は [sync-architecture.ja.md](sync-architecture.ja.md) の「クラウド認証」を参照。
- **Android の Google Drive** は、Google Play 開発者サービスがインストール済みかつ有効かつ最新の端末でのみ
  利用できる。Android では Google の Play 開発者サービス `AuthorizationClient` を使う。Play 開発者サービスが
  機能しない端末、および F-Droid 版には Google Drive を選択肢として出さない。アカウントと同期ファイルは
  デスクトップ版と共通。詳細は [sync-architecture.ja.md](sync-architecture.ja.md) の「Android での Google Drive」を参照。
- 同期ファイル形式、`VACUUM INTO` スナップショット、除外するローカル専用テーブル/インデックス、OAuth 詳細、
  トークン保存、マージ動作については [sync-architecture.ja.md](sync-architecture.ja.md) を参照。
- 同期対象: 購読リスト・フォルダー・既読状態・スター・タグ構造・記事本文・グローバル設定。
- 非同期対象: デバイスローカル設定・クラウド認証情報。
- インポート / エクスポートは OPML。
- 既読・未読やスターの変更は、記事 1 件ごとに同期するのではなくまとめて他のデバイスへ反映する — 読む操作が
  数分途切れたとき、アプリがフォアグラウンドを離れたとき、または次の更新・手動同期のとき。購読・フォルダ・
  タグ・設定の変更は従来どおり数秒以内に同期する。[sync-architecture.ja.md](sync-architecture.ja.md) 参照。
- 同期の実行中は、設定画面のクラウド同期タブで接続中プロバイダーの行に現在の進行状況を表示するため、
  時間のかかる初回同期でも止まっているように見えない。
- **Android と iOS では、自動同期は既定で Wi-Fi を待つ。** 同期のたびにデータベース全体をアップロード
  するため、自動同期は従量制回線（モバイルデータ通信・テザリング・従量制に設定した Wi-Fi）と OS の
  データセーバー / 低データモード中は保留し、回線が許せばすぐに同期する。設定画面のクラウド同期タブの
  「モバイルデータ通信でも自動で同期する」（既定はオフ、端末ローカル）で従量制回線での同期を許可できるが、
  データセーバー / 低データモード中は常に保留する。「今すぐ同期」と「すべて更新」は常にその場で同期する。
  プル更新は、選択中のスコープにフィードがあり、かつプロバイダーが接続されている場合にその場で同期する。
  デスクトップと macOS は制限しない。[sync-architecture.ja.md](sync-architecture.ja.md) の
  「ネットワークゲート」参照。

## 5. 競合解決ポリシー

| データ | ポリシー |
| --- | --- |
| 既読・未読、スター | タイムスタンプ後勝ち（`read_at` / `starred_at`） |
| 記事本文 | OR マージ（どちらかにあれば保持） |
| 購読リスト（追加） | OR マージ |
| 購読リスト（削除）、タグ・フォルダー、グローバル設定 | タイムスタンプ後勝ち（論理削除で伝播） |
| デバイスローカル設定 | 同期しない |

詳細は [sync-architecture.ja.md](sync-architecture.ja.md)。

## 6. セットアップフロー

初回起動でローカルのみ / クラウド同期（Dropbox・OneDrive・Google Drive。Android では Google Drive は
Google Play 開発者サービスがインストール済みかつ有効かつ最新の端末でのみ表示される、§4 参照）を選択する。クラウド選択時は OAuth 認証後、クラウドに既存データがあれば初回同期で自動的に
マージ（インポート）される。

## 7. 基本機能

- URL 指定でのフィード購読、タグによる分類、OPML インポート/エクスポート。`.opml` ファイルは
  他アプリから直接開くことでもインポートできる — デスクトップではファイル関連付けによる
  ダブルクリック、Android ではファイルマネージャやメール添付からの「Keryx で開く」、macOS/iOS では
  Keryx で開く。どこから始めても（設定 ▸ データのボタン、ファイルメニュー、開いたファイル）、
  インポート・エクスポートは設定 ▸ データで実行され、進行と結果はそこにインライン表示される。
  初回セットアップ中に開いた `.opml` はセットアップ完了後に取り込まれる
- フィードが1件も購読されていない間は、記事一覧に通常の「記事がありません」の代わりに
  「フィードを追加」ボタン付きの空状態メッセージを表示する。Android の狭い幅では、
  フィード一覧自身の「+」ボタンを持つナビゲーションドロワーがこの場面で自動的に開くことがある
  （正確な条件は §9「それより狭い幅」参照）ため、ユーザー自身がドロワーを探さなくても
  ボタンに届くようにしている
- フィード健全性管理: 301/308 は購読 URL を自動更新（通知）、410 Gone は通知センターに警告、
  連続エラーはフィード一覧にインジケータ表示
- アプリ内アップデート（リリースページへのリンクだけでなく、ダウンロード＋インストールまで）。
  Windows / Linux / Android に対応し、macOS では Sparkle 経由で更新する。更新は通知センターのベル、
  デスクトップのタスクトレイ、アプリメニューから提示され、いずれの経路を選んでも設定 ▸ アップデートを
  開く。ダウンロードとインストールは常に個別の明示的なユーザー操作であり、ダウンロードしたファイルは
  インストール前に GitHub リリースの SHA-256 ダイジェスト（macOS では EdDSA 署名）で検証する。
  その場で更新できないインストール形態（Linux の deb/rpm/Snap、Android の Google Play / F-Droid 版）は
  リリースページを開く。F-Droid 版はこの機能自体を持たない。詳細は
  [background-update.ja.md](background-update.ja.md) と [SECURITY.ja.md](../SECURITY.ja.md) を参照。
- 記事一覧・記事ビュー（リーダービュー）。**記事を選択した瞬間に既読**。未読に戻す操作あり。リーダーのツールバーのボタンは既読／未読のトグルで、記事の状態を表示する（未読の間は一覧の未読ドットと同じ塗りの丸）。リーダーだけが表示されていて一覧が見えない状態でも、タップした結果がわかり、元に戻せる。
  リーダーをスワイプして記事間を移動する場合（§9 参照）、「選択した瞬間」とはスワイプが記事の上に
  落ち着いた瞬間を指す——リーダーが次に備えて用意している隣の記事は、読み込まれてはいるが選択されて
  おらず、実際にスワイプして到達するまで未読のままである。
- **記事一覧は「すべて」「未読」「スター付き」の 3 つのモードのいずれかで表示する。** スター付き記事は
  ほぼすべて既読なので、2 つの独立した絞り込みではなく 1 つを選ぶ形にしている。現在のモードは記事一覧
  ツールバーの先頭にあるポップアップボタンに表示し、表示メニューにも 3 つのチェック項目として並び、
  ⌘/Ctrl+1・2・3 で選べる。**スター付き** は選択中のもの（フィード・フォルダー・タグ・すべてのフィード、
  検索結果を含む）をスター付きの記事に絞り込み、そのセッション中だけ維持される。購読一覧の「スター付き」
  項目を選んでいる間は、チェックを付けたまま無効で表示する。**すべて / 未読** は保存され、次回起動時に
  復元される。詳細は [app-architecture.ja.md](app-architecture.ja.md) を参照。
- **「未読」モードは、記事が既読になった瞬間には一覧から外さない**（読み進めている最中に一覧がずれない
  ようにするため、意図的な仕様）。一覧に残した既読記事（選択中の記事を除く）は、利用者が次に更新したとき
  （すべて更新、または下に引く）、手動で同期したとき、別のフィード・フォルダー・タグに切り替えたとき、
  別のモードから「未読」を選んだときに外れる。どれも「未読」モードからは抜けない。表示メニューの「既読記事を
  非表示」（デスクトップと macOS、iPad のハードウェアキーボード）を使えば、更新せずにいつでも同じことができる。
  隠す対象（選択中の記事以外の既読記事）が無いとき、または「未読」以外のモードのときは無効になる。
  ツールバーのボタンにはあえてしていない。上の経路があればめったに要らず、ツールバーの場所はよく使う操作に
  回すためである。幅の狭い iPhone では、6 つ目の項目があると「すべて既読にする」が「…」に押し出される。
- **現在のスクロール位置より一覧の新しい側の端寄りに届いた新着記事は、気づかれないまま静かに
  積み重なるのではなく、フローティングのピル**（例：「新着 12 件」）**として提示される**——
  タップするとその新着記事へ直接ジャンプする。新しい側の端は並び順に従い、そこまでスクロールすればピルは消える。
  一覧の途中や古い側に入った記事は数えない。ピルはウィンドウ幅やプラットフォームを問わず、
  手動更新／バックグラウンド更新、pull-to-refresh、クラウド同期のマージなどで一覧を開いたまま新着が
  発生したときに現れる。**それまで記事が 1 件も無かった一覧に初めて記事が入ったとき**や、
  既存の記事が一覧に入り直しただけの場合（スターの付け直し、フィードの移動など）は新着とは数えない。
- スター（永続）、外部ブラウザーで開く。「ブラウザーで開く」（およびフィードの「サイトを開く」）は `http`/`https`
  のリンクだけが対象で、それ以外のスキームや相対リンクは OS に渡さない——どの経路（ツールバー・メニューバー・
  ショートカット・コンテキストメニュー）でも項目は表示したまま無効になる。一方「URL をコピー」は空でない
  リンクなら何でもコピーできる。記事のリンクはフィードから検証なしで届くため、`file:`・`javascript:`・独自
  スキームのリンクで別のアプリケーションが起動されるのを防ぐ。
  Android では `http`/`https` のリンクを Custom Tab（ユーザーの既定ブラウザーのアプリ内タブ。アプリ内の
  ライト／ダーク設定に合わせた配色で、ブラウザーの共有操作も使える）で開くため、戻る操作でそのままアプリに
  戻れる。Custom Tabs に対応したブラウザーが入っていない端末では、既定のブラウザーで開く。
- **リンクの共有（Android のみ）。** 記事のリンクをシステムの共有シートで他のアプリへ送れる——リーダーの
  ツールバーと記事行の長押しメニューから実行でき、有効になる条件は「URL をコピー」と同じ（空でないリンク
  なら何でも）で、記事のタイトルを共有の件名として渡す。デスクトップには共有の操作はどこにも無い。逆向きに、
  他のアプリ（ブラウザーの共有メニューなど）から Keryx へ共有されたリンクは、共有テキスト中の最初の
  `http`/`https` URL を入力済みにした「フィードを追加」ダイアログを開く。テキストのそれ以外の部分や、
  他のスキームは無視する。ユーザーがダイアログで確認するまで何も購読しない。初回セットアップ中に共有された
  リンクはセットアップ完了まで待ち、ダイアログを開いている最中に共有されたリンクは入力中の内容を置き換える。
- SQLite FTS5 によるローカル全文検索。検索は現在選択中の購読リストの範囲（すべてのフィード／
  スター付き／特定のフィード／フォルダ／タグ）を絞り込む。検索語やランク付けの詳細は
  [db-schema.ja.md](db-schema.ja.md) を参照。
- デスクトップ通知・タスクトレイ常駐（閉じるとトレイに収納）・通知センター・未読バッジ。
  バックグラウンド更新後はクラウド接続時に同期が続く。従量制回線やデータセーバー / 低データモード中の
  バックグラウンドの同期とフィード更新は §4 の規則に従う。Android では新着通知とバックグラウンド更新を
  OS の経路で実行し、アプリ内の「アップデートを確認」は Google Play または F-Droid 版では非表示になる。
  iOS も同様にバックグラウンド更新と通知を行う。プラットフォーム固有の詳細（Linux の D-Bus、Android の
  WorkManager、iOS の BGAppRefreshTask、バッジ数、通知権限など）は
  [background-update.ja.md](background-update.ja.md) を参照。

### フィード URL 変更・消滅時の挙動

| HTTP | 挙動 |
| --- | --- |
| 301 / 308（恒久） | 購読 URL を自動更新（通知） |
| 302 / 303 / 307（一時） | 追従するが購読 URL は変更しない |
| 410 Gone | 通知センターに警告（自動削除はしない） |
| タイムアウト | 定数回リトライ後にエラー通知 |

## 8. アクセシビリティ・国際化

- UI 文言はすべて Compose Resources（英語の `values/strings.xml` ——既定かつフォールバック——に加え、
  同じキー集合の日本語 `values-ja/strings.xml`）で管理。システムロケールに応じて選択し、いずれの言語にも
  該当しなければ英語へフォールバック。SwiftUI アプリも同じ規則に従う（String Catalog はこれらのファイルから
  生成され、開発言語は英語）。
- 文字サイズ設定（`LocalDensity` の fontScale に反映）。OS 自身の文字サイズを置き換えるのではなく、その上に
  重ねて適用する（アプリの設定値をシステムのフォントスケールに乗算する）ため、システム全体で拡大した文字は
  Keryx でも拡大されたままになる。Android 14 以降の OS による非線形スケーリング（大きい文字ほど拡大率が
  小さい）も、乗算後のスケールに対して引き続き適用される。
- Android では、ステータスバーとナビゲーションバーのアイコン色は OS ではなくアプリ内のライト/ダーク設定に
  追従する（設定画面内も含む）。

## 9. UI 方針

**各プラットフォームは、単一の共通デザインシステムではなく、それぞれ自身のネイティブな UI 作法に従う。**
macOS はフラットで SF 寄りの見た目、Android は Material 3 自身のコンポーネント・形状・リップル
フィードバック、iOS / iPadOS は SwiftUI ネイティブ（§2 参照）。**Windows と Linux は意図的な例外** —
Java/Swing のプラットフォーム統合機能では両 OS を同程度にネイティブ化するのが難しいため、
macOS のフラットな見た目を共有する。Android 12+ では Material You のダイナミックカラーを使い、
古いバージョンでは固定のティール配色にフォールバックする。ライト/ダーク/システム対応。
3 ペインレイアウト（フィード一覧・記事一覧・記事詳細）+ キーボードナビゲーション。狭い幅では
同時に表示するペイン数を減らして適応する（後述）。

### 驚き最小

**アプリはユーザーが期待するとおりに動き、ユーザーが求めていないことはしない。**

- **求められていないことを起こさない。** ユーザー自身の操作なしに、画面遷移、ドロワーやダイアログの表示、
  フォーカスの移動、スクロール位置の変更、読んでいるリストの並べ替えや項目の削除、ユーザー自身の選択・
  絞り込み・設定の変更を起こさない。バックグラウンドで届くデータの反映はこれに当たらないが、
  ユーザーの操作を妨げない形で反映する（新着記事はリストをずらさずピルで知らせる、§7）。
- **操作はラベルやアイコンのとおりに動き**、見えない副作用を伴わない。
- **データや設定を失う操作は事前に確認する**——購読解除、フォルダやタグの削除、クラウド同期データの
  リセット、ファイルの上書き。既読化のように閲覧状態を変えるだけの操作は、あえて確認を挟まない。
- **プラットフォームの慣習を優先する。** ショートカット、戻る操作、メニューの位置、ジェスチャーは OS の標準に
  従う。意図して外れる場合は、その理由を本文書に書く。
- **同じ操作は、どの経路から実行しても同じに振る舞う**——後述の「複数の経路から実行できる操作」を参照。
- **端では何もしない**——何も起きないことを、別の効果で埋めない。

この原則に沿って既に決めている例: 「未読」モードでも既読になった記事を即座には隠さない; 「ブラウザーで開く」は
開けないリンクでは消さずに無効化して表示し続ける; キーボードフォーカスの枠線はハードウェアキーが押されてから
初めて出す; スクロール直後のスワイプはしばらく無視する; 先頭／末尾の記事で J/K を押しても何もしない;
通知の「フィードを表示」は狭いレイアウトのドロワーを開かない（[error-design.ja.md](error-design.ja.md) の `ShowFeedDetail`）。

### 更新のフィードバック

**進行中はすべての更新で表示し、結果はユーザーが始めた更新でだけ表示する。** 自動の更新とは、起動時の更新、
アプリを開いている間の定期更新、バックグラウンド更新のこと。ユーザーが始めた更新とは、すべて更新、引っ張る操作、
フィードごとの更新のこと。

| フィードバック | 自動の更新 | ユーザーが始めた更新 |
| --- | --- | --- |
| 進行中: フィード一覧の行のスピナー、ツールバーの更新スピナー | 表示する | 表示する |
| 進行中: 引っ張りインジケーター、iOS の「新着を確認中…」 | 表示しない | 表示する |
| 結果: iOS のステータス（「新着記事が N 件あります」「新着記事はありません」、または失敗） | 表示しない | 表示する（実行中の自動の更新に合流した場合も含む） |
| 結果: 新着記事の OS 通知 | アプリが前面にない間だけ | 表示する（すべて更新と引っ張る操作。フィードごとの更新では出さない）。すでに走っていた自動の更新に相乗りした場合も表示する |
| 失敗: どのフィードにも接続できなかった | 通知センターに残す | 通知センターに残す |

理由:

- **進行中は常に示す。** 更新がすでに動いているとわかれば、重ねて更新（引っ張る操作、すべて更新）を始めずに済む。
  画面の端にあるツールバーのスピナーだけでは見落としやすい。ユーザーの手元で未読数が変わるとき、その理由も見える。
  どの表示も専用の枠の中に収まり、何も動かさない（驚き最小）。
- **結果は求められたときだけ示す。** 自動の更新の結果は、すでに画面でわかる: 未読数が増え、記事一覧に記事が増え、
  新着ピルが出る（§7）。何も見つからなかった更新は知らせる必要がなく、どのフィードにも接続できなかった更新は
  どちらの場合も通知センターに残る。頼まれていない結果を出すと、ものが動く: iOS 26 より前はこのステータスが
  下部バーの唯一の項目なので、バーが出たり消えたりする（驚き最小）。
- **ユーザー自身の操作には必ず結果を返す。** 結果はその操作への応答だから。操作が新しい更新を始めず、実行中の
  自動の更新に合流した場合も同じ。
- **OS 通知は、アプリが前面にないときのためのもの。** 前面では未読数とピルが同じことを伝えるので、自動の更新の
  通知は出さない。ユーザーが始めた更新では出す: デスクトップと Android では、それがその操作の唯一の結果表示だから。
  「前面」とは、メインウィンドウにフォーカスがある（デスクトップ）、メインウィンドウがキーウィンドウ（macOS）、
  アプリの Activity が前面にある（Android）、アプリがアクティブ（iOS）こと。設定ウィンドウが前面のときは含めない
  （[background-update.ja.md](background-update.ja.md) を参照）。

### 複数の経路から実行できる操作

**ツールバーのボタン・アプリケーションメニュー・コンテキストメニュー・キーボードショートカット・
ジェスチャーなど、複数の経路から実行できる操作は、どの経路を経由しても同じように振る舞う**: 効果も、
有効/無効の状態も、フィードバックも同じである。経路によって違ってよいのは *どの項目に作用するか* だけで、
その項目に何が起きるかは変わらない。実装は共通化され、すべての経路は同じハンドラーを呼ぶ。特定の
画面上のコントロールに紐づくフィードバックは、そのコントロールが作用対象の項目を表示している限り
表示される。OS ごとのコピー確認の扱いなど、プラットフォーム固有の詳細は
[error-design.ja.md](error-design.ja.md) の「通知センター」を参照。

特定のペインでしか効かないキーは、それが効くときだけメニュー項目の横に表示される: フィード ▸ 名前変更・
削除はフィード一覧の項目が選択されていれば常にクリックできるが、F2（macOS では Return）と Delete を
表示し、それに反応するのは、フィード一覧がキーボードフォーカスを持ち、テキスト欄に入力中でないときだけである。

### 幅による適応レイアウトとタッチ入力

**3ペイン幅。** ウィンドウは3ペインが必要とする幅より狭くはならないため、フィード一覧を
常設のサイドバーとして、3ペインすべてを表示する。

**それより狭い幅。** フィード一覧はナビゲーションドロワーになり、ハンバーガーボタンから開くほか、
フィードもクラウドアカウントも無い初回起動時は自動的に開く。スマートフォン幅では記事一覧とリーダーの
うち1枚を、タブレット幅では両方を同時に表示する。ペイン自体の内容は変わらず、同時に表示する数だけが
変わる。Android の電話幅でリーダーから記事一覧へ戻る操作は、システムがサポートしていれば予測型バックを
使う。

**検索欄の配置。** 3ペイン幅では検索欄はフィード一覧のサイドバーにあり、結果は隣の記事一覧に表示される。
それより狭い幅ではドロワーに検索欄は無く、常に画面に残る記事一覧のヘッダーから検索に入る。iOS アプリも
同じ原則で、検索欄は常に記事一覧に置かれる。詳細は [app-architecture.ja.md](app-architecture.ja.md) を参照。

**マウスとタッチのアフォーダンス。** マウスとタッチスクリーンで異なるジェスチャーが必要な箇所は、
根底の操作を変えずに両対応する。マウスではクリック&ドラッグ、タッチでは専用ハンドルからのドラッグ。
デスクトップの右クリックは Android では長押しメニューになる。Android タブレットに物理キーボードが
接続されていれば同じキーボードショートカットも使える。詳細は
[app-architecture.ja.md](app-architecture.ja.md) を参照。

**スクロールとリーダー。** スクロール位置の見せ方はプラットフォームごとの作法に従う。記事リーダーは
実ブラウザビューを使う。Linux arm64 ではネイティブ WebView が存在しないため、Compose 描画の簡易表示に
フォールバックする。詳細は [app-architecture.ja.md](app-architecture.ja.md) と
[known-issues.ja.md](known-issues.ja.md) を参照。

**記事間のスワイプ。** 狭いレイアウトでは、リーダー上の水平スワイプで次/前の記事へ移動できる。縦方向の
移動量が横方向より明らかに小さくない場合はスクロールとして扱い、スクロール直後はしばらく無視する。
リーダーがデスクトップより狭い幅で画面上にあれば常に有効。3ペインレイアウトではリーダーはキーボード
操作前提（J/K）であり、スワイプは適用されない。[app-architecture.ja.md](app-architecture.ja.md) の
「Home の適応的ペインレイアウト」を参照。

**引っ張って更新。** Android と iOS / iPadOS ネイティブアプリでは、記事一覧を下に引っ張ると、
選択中の項目に応じた範囲のフィードを更新する。iOS ではサイドバーを引っ張ると「すべて更新」になる。
検索結果表示中やフィードが無いときは無効。表と詳細は [app-architecture.ja.md](app-architecture.ja.md) の
「更新の表示と引っ張って更新」を参照。

**iOS の更新状況表示。** iOS には回転させる「すべて更新」ボタンが無いため、ユーザーが始めた更新（プル、
「すべて更新」、フィード単体の「更新」）をボトムバー中央に表示する: 実行中（続くクラウド同期を含む）は
スピナーと「新着を確認中…」、終わると約 2.5 秒だけ結果——「新着記事が N 件あります」「新着記事はありません」、または
どのフィードにも接続できなかったときは警告記号付きの失敗メッセージ（通知センターにも残る）——を表示する。
自動の更新や同期だけのときは何も表示せず、待機中も何も表示しない。前述の「更新のフィードバック」と、
[app-architecture.ja.md](app-architecture.ja.md) の「更新の表示と引っ張って更新」を参照。

**フィードごとの更新スピナー。** フィードの更新中は、何が始めた更新であっても、対象となる各フィードが
フィード一覧のアイコンの位置に小さなスピナーを表示し、そのフィードの新着記事が反映されるまで続く
（全プラットフォーム共通）。折りたたまれたフォルダーは、配下のフィードのどれかがスピナーを表示している間
同じスピナーを表示する。行の中身は動かず、スクリーンリーダーには行の状態が「更新中」と読み上げられる。

**ネイティブメニュー、トレイ、ファイルダイアログ、フォント。** デスクトップアプリはメニューバー、
コンテキストメニュー、トレイメニュー、ファイルダイアログに Swing/AWT ウィジェットを使う。
プラットフォーム固有の選択（macOS/Windows/Linux、FlatLaf、Linux の JFileChooser など）は
[app-architecture.ja.md](app-architecture.ja.md) と [known-issues.ja.md](known-issues.ja.md) を参照。

## 10. プライバシー・セキュリティ

- 開発者が運営するサーバーはなく、アカウント登録も不要。Keryx が通信するのは利用中の機能に直接
  関係するサーバーのみ（購読中の各フィードとその favicon、更新チェック/ダウンロード用の
  GitHub、接続している場合のみ Dropbox / OneDrive / Google Drive）で、常に端末から直接行う——
  完全な一覧は [PRIVACY.ja.md](../PRIVACY.ja.md)「アプリが行う通信」を参照。
  Keryx 自身の通信（クラウド同期・更新チェック・
  更新ダウンロード）は常に HTTPS を使用する。購読フィードは、URL が明示的に `http://` である場合
  （またはそこへリダイレクトされる場合）は平文の HTTP で取得される——スキームを指定しない
  フィード URL は HTTPS に補われるが、明示的な `http://` は上書きしない。ただしリーダーは画面に
  出ている記事の両隣をスワイプで移動できるよう用意しておく（§9）ため、それらの本文は——含まれる
  画像や埋め込みコンテンツも含めて——開く前に、開いたときと同じように取得される。それらが既読に
  なることはない。
- 各クラウドプロバイダー（Dropbox・OneDrive・Google Drive）のトークンはそれぞれ独立してプラットフォームの
  セキュアストレージに保存する。macOS: アプリのデータ保護キーチェーン（ファイルへのフォールバックなし）。Windows/Linux は
  Credential Manager / Secret Service（java-keyring 経由）、Snap 版だけはデスクトップの Secret portal から
  得たアプリ専用の鍵で暗号化されたローカルストア（libsecret 経由。java-keyring は使わない）——利用不可時は
  データディレクトリのファイルにフォールバック。Android: プロバイダーごとに Android Keystore が保持する
  AES-256/GCM 鍵。両方の詳細は `sync-architecture.ja.md`「Token Storage」参照。

## 11. 技術選定

| レイヤー | 採用技術 |
| --- | --- |
| UI | Compose Multiplatform（Android は Material 3、macOS/iOS は SwiftUI ネイティブ、Windows/Linux はフラットなデスクトップ見た目を共有 — §9 参照） |
| 状態管理 | androidx.lifecycle ViewModel + Koin |
| DB | SQLDelight（SQLite）+ FTS5（生 SQL） |
| HTTP | Ktor client（desktop は CIO、Android は OkHttp） |
| RSS/HTML/XML パース | ksoup |
| シリアライズ / 日時 | kotlinx-serialization / kotlinx-datetime |
| クラウド同期 | Ktor + Dropbox / OneDrive（Microsoft Graph）/ Google Drive REST API（OAuth PKCE + リフレッシュトークン） |
| i18n | Compose Resources |
| テスト | kotlin-test + kotlinx-coroutines-test + Ktor MockEngine |
| ビルド | Gradle 9.7.1（Kotlin 2.4.10 / Compose Multiplatform 1.11.1 / JDK 25 toolchain） |
| 画像ロード | Coil3（favicon 表示。SVG デコード対応、既存 HttpClient 共有、ディスクキャッシュあり） |

フィード一覧・記事一覧の両方で、favicon（`feeds.favicon_url`）を Coil3 の `AsyncImage` で表示する。
未取得・読み込み失敗時はレター（頭文字）アバターまたは汎用アイコンにフォールバックする。
