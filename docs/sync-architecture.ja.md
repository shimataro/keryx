# 同期アーキテクチャ

[English](sync-architecture.md)

対象: クラウドストレージ同期（Dropbox / OneDrive / Google Drive / Nextcloud）。実装は `domain/SyncRepository.kt`
（スケジュール、ゲート、ユーザーに見せる状態）、`domain/DeltaSync.kt`（以下のフロー）、`domain/SyncPointer.kt`、
`domain/TransportCoverage.kt`（ベースが何を覆うか、ベースのキャッシュ、記録した送信）、`domain/LegacyCloudFile.kt`
（差分同期以前の形式からの移行と旧ビルドの監視）、`domain/MergeSql.kt`、
`domain/ReduceSql.kt`、`domain/TransportSchema.kt`、`domain/MergeFailureClassifier.kt`、`domain/MergeSchema.kt`、
`domain/DeltaExportSql.kt`、`domain/TagFolderIdRekey.kt`（v2→v3 のタグ/フォルダー id 振り直し）、`platform/DatabaseMerger`、`platform/DeltaExporter`、`platform/TransportFiles`。

## 設計方針

- **差分同期。** 各端末は自分で起こした変更だけを、作成後に変更しない小さな差分ファイルとしてクラウドに追記し、
  ほかの端末がそれをマージする。差分が一定量たまったら、どの端末でも、それを全体のスナップショット（*ベース*）に
  畳み込む。単に存在するというだけでデータを再アップロードすることはなく、何も変わっていない同期はペイロードを
  1 バイトも転送しない。
- **操作ではなく状態を送る。** 差分が運ぶのは、変更された各行の**現在の状態**（フィールドごとの後勝ちスタンプ付き）
  であり、「記事 X にスターを付ける」といった操作ではない。マージはフィールドグループごとの後勝ちなので、
  **冪等**（同じファイルを 2 回適用しても何も変わらない）、**可換**（ファイルの到着順に依存しない）、**結合的**
  （1 つずつマージしても、畳み込んでからマージしても同じ）である。そのため、ファイルの重複、順序の逆転、クラッシュ
  後の再適用はすべて無害であり、この文書の残りはこの性質に依拠している。
  まだ塞いでいない既知の例外は [known-issues.ja.md](known-issues.ja.md) に記録してある: URL が同じで id が違う
  フィード、そしてフォルダーの削除と復活をまたいでフィードが削除済みフォルダーを指し続けること。（3 つ目にあった
  「名前が同じで id が違う行」は、タグとフォルダーの id が名前から決まるようになって塞がれた:
  `IdGenerator.tagId` / `folderId`。v2→v3 移行が一度だけ振り直すので、2 台が同じ名前を独立に作れば同じ id となり、
  マージはタグとフォルダーを id だけで照合する。振り直された行は移行前の id を `v2_id` に保つ。移行前に別々の名前へ
  リネームした 2 台の行は同じ `v2_id` を持つので、マージはあらゆる種類のファイルでそれらを先に 1 つの同一性へ
  再統合する。バージョン 3 は未リリースだが、暫定のランダム id でバージョン 3 を
  すでに走らせた開発環境は振り直されない——コールバックはバージョン 2 をまたぐときしか発火しない——ため、
  クラウド同期データを一度リセットする必要がある。）
- **送るのはローカルの変更だけ。** マージで入ってきた変更は再送しないので、変更が端末間を往復し続けることはない。
- **どの変更も到達不能にしない。** すべての変更は、常にクラウド上の少なくとも 1 つの差分ファイルかベースに含まれて
  いる。ファイルの削除は、この性質を保つガベージコレクションの規則に従うときだけ行う（「ベースとガベージ
  コレクション」参照）。
- **転送ファイルは SQLite**（gzip 圧縮）で、専用の*転送用スキーマ*を使う——同期対象のテーブルと列だけを持ち、
  UNIQUE 制約と外部キーを持たず、メタ情報の表がいくつか加わる。マージはこれまでどおり `ATTACH DATABASE` で
  アタッチする。
- **DB をメモリに載せない。** `CloudStorage` はローカルのファイルパスで受け渡しする——`download(path, destPath)` は
  レスポンスボディをそのままディスクへ、`upload` / `create` はファイルをそのまま送信へストリームする——ので、
  ピークメモリは 64KB バッファ数個分の固定量である。共通のストリーミングヘルパーは
  `data/cloud/CloudFileTransfer.kt`（`kotlinx-io` 実装、`commonMain`）にある。

## クラウド上のファイル構成

名前はフラットにする: Google Drive・OneDrive・Nextcloud はファイルをベース名だけで扱うため、各ファイルの種類は
フォルダーではなく名前に埋め込む。

```bash
/keryx-sync.json                                     ← ポインタ: {"format":3,"generation":"<genId>"}。リビジョンチェック付きで更新
/ks-<gen>-b-<dev>-<n>-<createdAt>-<hash12>.db.gz     ← ベース: 全同期対象行を畳み込んだもの（作成後は不変）
/ks-<gen>-d-<dev>-<seq>-<createdAt>-<hash12>.db.gz   ← 差分: 端末 <dev> の <seq> 番目の変更（作成後は不変）
/keryx.db.gz                                         ← 移行後: user_version が 1000 のスタブ（「移行」参照）
/keryx-YYYYMMDD-HHMMSS.db.gz.bak                     ← 差分同期以前のファイルの退避（自動削除されない）
```

- `<gen>` はポインタが指す現在の**世代**。クラウドデータのリセットは新しい世代を始める。古い世代のファイルは
  退避としてそのまま残し、二度と読まない。
- `<dev>` は書き込んだ端末の同期 ID（`sync_state.ks_device_id`）で、端末が世代に参加するたびに新しく発行する。
- `<createdAt>` はファイルの作成時刻（Unix ミリ秒の 10 進表記）で、その `ks_meta.created_at` と同じ値。差分の
  古さが名前に入るので、ベースのベクトルがその差分を含意してよいかを一覧だけで判断できる（「転送用スキーマ」参照）。
- `<hash12>` は*展開後*のファイルの SHA-256 の先頭 16 進 12 桁。同じ名前のファイルは必ず同じ内容なので、すべての
  書き込みを、原子性が問題にならない単純な `create` にできる（Google Drive の create は原子的でない）: 同じ名前の
  2 回目の `create` は同じファイルであり、異なるファイルが同じ名前を持つことはない。ダウンロードのたびに照合する。
- 名前は使う前に厳密なパターンと照合し、合わないものは他人のファイルとして無視する（Nextcloud の `/Keryx` フォルダー
  には利用者自身のファイルがありうる）。SQL に埋め込むのは、パターンを通った名前だけである。

競合が起こりうるのは、置き換えられることのある 2 つのファイル——ポインタと `keryx.db.gz` のスタブ——だけで、
どちらもプロバイダーのリビジョンチェック付きで書く（Dropbox: `rev`、サーバー側の本物の compare-and-set。
Google Drive: `<id>:<version>` をクライアント側で比較するため原子的でない——[known-issues.ja.md](known-issues.ja.md) の
「Google Drive: アップロードが他端末のアップロードを気付かれずに上書きすることがある」参照。OneDrive: `eTag` を
`If-Match` で送信。Nextcloud: `ETag` を `If-Match` で送信し、412/423 → 競合）。lock ファイルは使わない。
Nextcloud では、これらのファイルはアプリフォルダーではなく利用者自身のファイルの `/Keryx/` フォルダーに置く。

### 一覧取得（`CloudStorage.list`）

`list(prefix)` は、名前が `prefix` で始まるすべてのファイル（名前・リビジョン・サイズ）を、全ページをたどって返す:
Dropbox は `list_folder` / `list_folder/continue`、Google Drive は `appDataFolder` での `files.list` と
`nextPageToken`、OneDrive はアプリフォルダーの `/children` と `@odata.nextLink`、Nextcloud は `/Keryx` への
Depth 1 の `PROPFIND`。既にたどったページ指定（カーソル、ページトークン、`nextLink`）が再び返った場合は、ループせず
ストレージエラーとする。Drive と OneDrive の一覧は結果整合で、書いた直後のファイルがしばらく見えないことがあるが、
受信の規則はこれを許容する（欠番はカーソルを止めるだけで、何も飛ばさない）。Drive は同名のファイルを 2 つ返す
こともあるが、同期ファイルでは同じ内容のコピーが 2 つあるという意味にしかならない。

### 転送用スキーマ（`domain/TransportSchema.kt`）

差分とベースは、同期対象の 6 テーブル（`feeds`、`articles`、`tags`、`feed_tags`、`folders`、`global_settings`）を、
同期対象の列だけで持つ——`feeds` の取得状態（端末ローカルの `feed_fetch_state` に移った）と
`articles.search_text`（受信側で再計算する）は含まない——。UNIQUE 制約と外部キーも持たない: ベースは複数の端末の
行を畳み込み、リネームが同名の作成と交差すれば、1 つのタグ名やフォルダー名を 2 つの別々の id が持つことは正当に
ありうる（行の名前由来 id は「元の名前」から導かれたもの）。タグやフォルダーの `v2_id`——v2→v3 の振り直し前に
その行が持っていた id で、移行後に作られた行では NULL——も一緒に運ぶので、受信側は、アップグレード前に 2 台が
別々の名前にリネームした行を再統合できる（「マージ」参照）。各ファイルは `PRAGMA user_version` と、
次の表を持つ:

- `ks_meta(key, value)` — `format`（形式）、`generation`（世代）、`device`（書き込んだ端末）、`created_at`（作成時刻）、
  `kind`（種別、`delta` / `base`）、`number`（差分の `seq` またはベースの `n`）。generation・device・kind・number・
  作成時刻はファイル名と一致しなければならない
- `ks_vector(device, seq)`（ベースのみ）— 端末ごとに、差分 `1..seq` がすべて含まれている最大の `seq`
- `ks_covered(name, created_at)`（ベースのみ）— このベースが畳み込んだ差分ファイルのうち、ベクトルが含意**しない**
  もの。それぞれ差分自身の作成時刻（その `ks_meta.created_at`。不明なら NULL）を持つ

ベースは差分 `(device, seq)` を、ベクトル（`seq ≤ ks_vector[device]`）か名前（`ks_covered`）で覆う。ベクトルが差分を
含意するのは、差分がベース自身より `KS_DELTA_GRACE_MS` 以上前に作られていて（2 つの名前の作成時刻で比べる。
`BaseCoverage.vectorCutoff`）、かつ `ks_covered` が同じ `(device, seq)` の差分を 1 つも挙げていない間だけである。
どちらの規則も、別々のファイルが 1 つの `(device, seq)` を共有するとき——複製されたデータベースが書いたとき、または
作ってから長くたってアップロードされた送信のとき——ベースが畳み込んでいないファイルが含意されないようにする。
ベースの基準時刻より後に作られたコピーは決して含意されないので、どのベースにも覆われていない差分と同じく受信され、
畳み込まれ、残される。また、ベースが畳み込んだコピーは、すべて列挙されるので、見ていないコピーが含意されることも
ない。ベクトルは `(device, seq)` そのものについては引き続き有効である——受信のカーソルと隙間の探索は、ファイル
ではなく番号で判断する。したがって `ks_covered` は、これまで畳み込んだすべての差分とともに増え続けることは
なく、小さいまま保たれる——直近 `KS_DELTA_GRACE_MS` の差分、隙間より先の差分、複製のコピーだけ（ベクトルを
いつ伸ばしてよいかは「ベースとガベージコレクション」参照）。

`TransportSchema` は、DDL、バージョンごとの期待される表・列・型、転送用のマイグレーションを持つ。
`KeryxDatabase.Schema.migrate` は転送ファイルには決して実行しない（端末ローカルの表とトリガーが加わってしまう）。

## ローカルの管理情報（スキーマバージョン 3）

| オブジェクト | 用途 |
| --- | --- |
| `sync_outbox(seq INTEGER PRIMARY KEY AUTOINCREMENT, tbl, pk, pk2, heavy)` | 同期対象行へのローカルの変更を、順に記録する |
| `sync_capture(id = 1, enabled, full_pending)` | 変更を記録するか（接続中のみ）と、全量送信が必要か |
| `sync_merging(flag)` | マージのトランザクションの中にだけ存在する（最初に INSERT、`COMMIT` 直前に DELETE）ので、ほかの接続からは決して見えない |
| `sync_applied(name)` | マージ済みのクラウドファイル（この端末自身のものを含む） |
| `sync_cursor(device, seq)` | 端末ごとに、すべての差分をマージし終えている最大の `seq` |
| `ks_search_pending(rowid)` | `search_text` の再計算が必要な記事（「FTS5 の扱い」参照） |
| `ks_search_awaiting_body(id)` | マージが本文なし（軽量行）で挿入した記事。本文が届くまで検索索引に入れない（「FTS5 の扱い」参照） |
| `ks_feed_folder_raw(feed_id, folder_updated_at, folder_id)` | フィードごとに、`feeds.folder_id` の解決後の値の元になった生のフォルダー版（勝ったファイルが持っていたままのもの）。スタンプがフィードの `folder_updated_at` と等しい間だけ有効（「マージ」参照） |
| `ks_id_remap(kind, old_id, new_id)` | v2→v3 移行が走らせたタグ/フォルダー id の振り直し（`domain/TagFolderIdRekey.kt`）の記録。`SettingsRepository` が移行後の最初の起動時に `local_settings.json` の同じ id を書き換える。その書き換えをべき等に保つため表は無期限に保持する。同期マージは事前アップグレード行の同一性をこの表ではなく行の `v2_id` で再統合する（[db-schema.ja.md](db-schema.ja.md) 参照） |
| `feed_fetch_state(feed_id, etag, last_modified, error_count, last_error)` | この端末でのフィードの取得状態——同期しない |

同期対象の 6 テーブルの**トリガー**（`AFTER INSERT` / `AFTER UPDATE`）が `sync_outbox` に追記する。条件は
`WHEN (SELECT enabled FROM sync_capture) = 1 AND NOT EXISTS (SELECT 1 FROM sync_merging)` なので、マージが書いた
ものは決して記録しない。`UPDATE` は同期対象の列が実際に変わったときだけ記録する（`OLD.x IS NOT NEW.x OR …`）
ので、変わらない行を書き直すだけのフィード更新は何も記録しない。記事については:

- `content`・`summary`・`title`・`url`・`author`・`published_at`・`thumbnail_url`、または本文のスタンプ
  `body_updated_at` の変更（または挿入）は `heavy = 1` で記録する——差分は記事の本文を運ぶ。
- 既読・スター・削除の列だけの変更は `heavy = 0` で記録する——差分は `content` と `summary` を NULL にした
  *軽い*行を運ぶ。
- `cached_at` は日付（`cached_at / 86400000`）が変わったときだけ記録する——フィード更新はフィードに残っている
  すべての記事でこれを更新するので、30 分ごとに送るとほかのすべての変更を圧倒してしまう（キャッシュ削除への影響は
  「同期対象の記事範囲」参照）。
- `updated_at` だけ、`search_text` だけの変更は記録しない。

同期対象テーブルの行を物理削除することはない（削除はすべて論理削除）ので、`DELETE` トリガーはない。

`sync_state` のキー: `last_synced_at`、`ks_device_id`、`ks_generation`、`ks_last_seq`、`ks_attempt`（送信中の
ファイルの番号・名前・outbox の上限・全量送信かどうか）、`ks_pointer_rev`（世代が `ks_generation` であるポインタの
リビジョン）、`ks_received_at`（この端末が最後に受信を終えた時刻。この端末の時計で）、`ks_bases`（この端末が自分の
世代のベースについて知っていること——それぞれのベクトル、`ks_covered`、作成時刻——で、ダウンロードせずにベースが
何を覆うかを判断するためのもの）、`ks_legacy_stub_rev`、`sync_index_pending`（マージのコミットから、検索インデックスが
それに追いつくまで存在する——「受信」参照。その作業はローカルの検索インデックスのものであり、接続を解除しても残すので、
`ks_` 接頭辞を付けない）。`sync_state` と上の表は端末ローカルで、
端末の外に出ることはない。

## 同期フロー（`SyncRepository.sync()`）

以下はすべて `SyncRepository` の `mutex` の内側で行う。

0. **中断した送信の再開**（手順 1 で世代がわかってから）。`ks_attempt` が設定されていれば、そのファイルはローカルに
   書かれ（アップロードもされたかもしれない）、確定されていない。名前の作成時刻から `KS_RESUME_MAX_AGE_MS`（12 時間）
   以内なら、保存されたファイルを展開して名前のハッシュと照合し、一致すれば同じ名前で再アップロードして確定する
   （「送信」の手順 4）。送信がそれより古い（またはこの端末にとって未来の時刻である）か、ファイルが無いか、ハッシュが
   一致しないか、記録そのものが読めなければ、端末は**新しい同期 ID**（新しい `ks_device_id`、`ks_last_seq = 0`）を取る: その試行が
   対象にしていた outbox の記録は削除されていないので新しい ID で送り直され、古い ID のファイルは、クラウドに
   届いていたとしても無害に適用されるだけである。ディスク上で壊れたファイルを送ることは決してなく、古いファイルも
   送らない: 古い作成時刻のまま遅れてアップロードすると、すぐにガベージコレクションしてよい古さに見え、ときどき
   しか同期しない端末が一覧で見る前に消されうるうえ、畳み込まれないままベクトルに含意されうる。新しい ID で送り
   直せば、同じ変更が新しい作成時刻を持つ。（この上限は `KS_RECEIVE_STALE_MARGIN_MS` より小さい。）世代がその後
   変わっていれば、試行は単に捨てる（再参加の全量送信に含まれる）。試行が記録されていなければ、データディレクトリ
   にある保存ファイル（`pending-<n>.db.gz`）はすべて残りもの——確定とその削除の間、または記録を消してから
   ファイルを消すまでの間のクラッシュで残ったもの——なので、すべて掃除する。新しい同期 ID を取るとき、参加のとき、
   接続解除のときも同じく掃除する。掃除は best effort で、消せないファイルはログに残して次の掃除に任せ、その前後の
   処理を止めない（アップロードされるのは記録された送信だけである）。
1. **ポインタを読む。** `metadata(keryx-sync.json)` を取り、リビジョンが `ks_pointer_rev` と違うときだけ
   ダウンロードする。
   - ポインタも完全な `keryx.db.gz` も無い（ファイルが無い、またはスタブ）→ 最初の端末になる（「参加」）——ただし、この端末がすでに自分の世代へ送信して
     いる（`ks_last_seq ≥ 1`: ポインタを作る前に中断した最初の端末）なら、その世代のポインタを作る。
   - ポインタは無いが `keryx.db.gz` がデータベース全体を持つ → 差分同期以前の形式から移行する（「移行」）。
   - 世代が `ks_generation` と違う → 再参加する（「参加」）——別の端末がクラウドデータをリセットした。
   - 解析できない、または項目が足りない → `CloudDataIncompatibleException`（リセットで書き直す）。
   - `format` がこのビルドの知るものより新しい → `SchemaVersionException`（「アプリを更新してください」）。
   - **旧ビルドの監視:** `metadata(keryx.db.gz)` も取る。リビジョンが `ks_legacy_stub_rev` と違えば、古いビルドが
     そこにデータベース全体を書いたということなので、取り込む（「移行」）。
2. `ks-<gen>-*` を**一覧取得**する（`CloudStorage.list`、全ページ）。この端末自身の `<dev>` を持つのに、この端末が
   書いていないファイル——`seq ≤ ks_last_seq` なのに名前が `sync_applied` に無い、または `seq > ks_last_seq` なのに
   `ks_attempt` の名前ではない——があれば、データベースが複製され（バックアップからの復元や、別のマシンへの
   コピー）、2 つのコピーが同じ端末として書いているということなので、この端末は新しい ID で再参加する。既知の
   ベースが覆う自分の差分は数えない（ガベージコレクションされても、しばらく一覧に出続けることがある）。受信の後、
   この端末の ID の `ks_last_seq` より上の差分を既知のベースが覆っていれば、同じ意味になる——猶予期間より古い
   バックアップから復元したコピーは、元の端末の新しい差分をベースを通してしか見られない——ので、送信の前に再参加
   する。その間も何も失われない——名前のハッシュが 2 つのコピーのファイルを区別し、受信側は両方を適用する。
3. **受信する**（「受信」参照）。
4. **送信する**（「送信」参照）。
5. 閾値に達していれば、**畳み込みとガベージコレクション**を行う（「ベースとガベージコレクション」参照）。
6. `last_synced_at` を記録する。

何もすることのない同期は、3 リクエスト（`metadata` 2 回と一覧 1 ページ）でペイロードは 0 バイトである。
`keryx.db.gz` の監視は、差分同期以前との互換処理の残りと一緒に v1.0.0 で廃止する。`SYNC_MAX_RETRY` が上限を
定めるのは、リビジョンチェック付きの書き込み（ポインタ、スタブ）の再試行だけになった。差分とベースの名前は衝突しない。

### 受信

1. **取得するもの。** 一覧にある差分のうち、名前が `sync_applied` に無いものすべて。さらに端末 D ごとに、
   `sync_cursor[D]` より上で、適用済みでも一覧にも無い `seq`——すでにガベージコレクションされた差分——を探す。
   それを覆うベースがあれば、そのベースも取得し、それが覆う一覧上の差分を適用済みとして扱う。ベースが何を覆うかは
   `ks_bases` から読み、この端末が一度も見ていない一覧上のベースは、それを知るためにダウンロードする。覆うベースが
   無ければ、プロバイダーの一覧がまだ追いついていないとみなす（Drive と OneDrive の一覧は結果整合）: カーソルは
   その手前で止まるが、ほかのファイルはすべてマージし（マージは可換）、次の同期でもう一度調べる。この端末に
   足りないものを覆う既知のベースも取得する。ベースが名前で挙げる差分（`ks_covered`）は、その名前自体が
   `sync_applied` にあるときだけマージ済みとみなす: カーソルが示すのは各 `(device, seq)` のどれか 1 つのファイルを
   マージしたことだけであり、カーソルより下の `seq` の複製による重複は別のファイルで、その変更はほかのどこにも
   無いかもしれない。
   - **参加時、または長く離れていたとき。** 参加時——および `ks_received_at` が `KS_DELTA_GRACE_MS` から
     `KS_RECEIVE_STALE_MARGIN_MS`（1 日。一覧の遅れと端末間の時計の差の分）を引いたより古いとき——は、この端末が
     知らない一覧上のベースをすべて取得する。差分がガベージコレクションされるのはその古さになってからなので（下記）、
     その期間内に受信した端末は消えうる差分をすべて見ている。そうでない端末は、隙間を残さずに消えた差分（静かに
     なった ID の最後の差分）を見逃しているかもしれず、それはベースにしか残っていない。`ks_received_at` を記録する
     のは、隙間を残さず、取り逃したファイルが無く、知っているベースを 1 つ以上見た受信だけである——したがって、
     世代のベースが一覧にまだ出ていない参加中の端末は、それが出るまで探し続ける。
   - **その間に消えたもの。** 一覧にあるのにダウンロードが失敗し、`metadata` でも見つからないファイル
     （ガベージコレクションされ、一覧が追いついていない）は、一覧に無いものとして扱う: そこからは何もマージせず、
     カーソルはその手前で止まる。
2. すべてのファイルを**検証**する（「クラウドファイルの検証」）。1 つでも失敗すれば、何もマージしない。
3. ファイルを `ReduceSql`（主キーごと・フィールドグループごとの後勝ち。マージと同じ規則で、ローカル用のガードは
   持たない）で 1 つの一時転送 DB に**畳み込む**ので、何個のファイルが届いてもマージは 1 回で済む。
4. `DatabaseMerger.mergeTransport` で、1 つのトランザクションとして**マージ**する（「マージ」参照）: 最初に
   `INSERT INTO sync_merging`、次に `MergeSql.all`、マージした全ファイルの `sync_applied` / `sync_cursor` の更新と
   `ks_search_pending` と `sync_index_pending` の登録、最後に `DELETE FROM sync_merging`。`sync_applied` に記録する名前には、マージした
   ベースが名前で挙げるものを、一覧にあるかどうか（その間にガベージコレクションされたか）によらずすべて含める。マージと、何をマージしたかの記録は一緒に
   コミットされるか、どちらもされないかのどちらかである——その間でクラッシュすれば次回に同じファイルを再マージ
   するが、マージの冪等性によって無害である。
5. コミットの直後: 同期対象の全テーブルについて `driver.notifyListeners(...)` を呼ぶ——マージは専用の接続で書くので、
   この後に何が起きても UI に反映するには、SQLDelight のフローを再発火させる必要がある。続いて
   `ftsManager.indexMissing()`（まず `ks_search_pending` の `search_text` を再計算する。「FTS5 の扱い」）を呼び、
   `articles` のリスナーにもう一度通知し（表示中の検索が、マージした行を索引済みの状態で見つける）、
   `sync_index_pending` を消す。索引付けが失敗すると、同期は一時的なエラーで失敗し、キーは残る: 次の同期は——マージ
   するものが無くても——`indexMissing()` をもう一度実行し、通知して、キーを消す。
6. 一覧から消えた名前は `sync_applied` から外す。再び現れても、もう一度適用するのは無害である。一覧上の既知の
   ベースが名前で挙げる名前は残す——外すと、手順 1 がそれを足りないものとみなし、同期のたびにそのベースを取得し
   直すことになる。この端末自身の差分は、既知のベースが覆うまで残す——送ったばかりの差分がまだ一覧に出ていなくても、
   複製のもの（手順 2）に見えることはない。

### 送信

1. **差分を作る。** `platform/DeltaExporter`（`commonMain`。SQL は `domain/DeltaExportSql` で、`TransportConnections` の
   プラットフォームごとの接続で実行する）が、新しい空の転送ファイルに専用の接続を開き、そこへ元のデータベースを
   `ATTACH` する:
   - **通常の差分**——1 つの読み取りトランザクションの中で: `S = MAX(sync_outbox.seq)` を読み、`≤ S` の outbox の
     記録を持つすべてのキーについて**現在の**行を書き出す。それらの行が参照する行（フィードのフォルダー、記事の
     フィード、`feed_tags` の行のタグとフィード）も含めるので、受信側のマージが参照先の行を見つけられないことは
     ない。`heavy` の記録が無い記事は軽い行として書く。`S` と行は 1 つのスナップショットから読まれるので、その後の
     書き込みはすべて `seq > S` を持ち、次の差分に入る。
   - **全量送信**（参加時）——差分同期以前のアップロードと同じく `VACUUM INTO` のコピーから書き出すので、ライブ
     DB の読み取りロックはコピーの間しか保持しない。`S` もコピーから読む。直前にマージしたベースと同一の行
     （`EXCEPT`）は除く——空のデータベースを持つ新しい端末は、ほとんど何も送らない。その後、残す行が参照する行を
     付け戻す（残した記事のフィード、残したフィードのフォルダー、`feed_tags` 行のタグとフィード）。これで、残した
     記事のフィードがマージ済みベースと同一でも、ファイルは検証チェック 9 を通る。
2. **アップロードの前に記録する**: ファイルの名前はエクスポーターの出力そのもののハッシュから付け（以後書き込み用に
   開くことはない——Android ではそれだけで `android_metadata` が加わり、バイト列が変わる）、圧縮してアプリのデータ
   ディレクトリに `pending-<n>.db.gz` として書き、`ks_attempt = (n = ks_last_seq + 1, name, S, full)` を記録する。
   行が 1 つも無いファイル——すべての行をクラウドがすでに持っている全量送信——はアップロードしない: それが対象に
   していた outbox の記録を消し、`full_pending` をその場で下ろす。
3. `create(name)` で**アップロード**する。「すでに存在する」という応答は、同じファイル（同じ名前は同じ内容）が
   あるという意味なので、成功として扱う。
4. 1 つのトランザクションで**確定**する: `DELETE FROM sync_outbox WHERE seq ≤ S`、`ks_last_seq = n`、名前を
   `sync_applied` に追加、全量送信だったなら `full_pending` を下ろす、`ks_attempt` を消す。そのあと保存した
   ファイルを削除する。

どこで中断しても、何も失われず、二重にもならない: 未送信の変更は outbox に残っており、クラウドに届いていた
ファイルは確定の前に同じ名前で送り直される（フローの手順 0）。

### ベースとガベージコレクション

**いつ。** 送信の後、既知のどのベースにも覆われていない一覧上の差分が `KS_COMPACT_MIN_DELTAS`（100）ファイル、
または一覧上で最大のベースのサイズの `KS_COMPACT_MAX_DELTA_RATIO`（25%）に達したとき。この端末が知らないベースは
先にダウンロードし——それらの差分をすでに覆っているかもしれない——閾値をもう一度確かめる。どの端末が畳み込んでも
よく、2 台が同時に行っても安全。従量制の回線やデータセーバー / 省データモードの下では、手動同期でも行わず
（`NetworkUsagePolicy.compactionAllowed`）、いつキャンセルされてもよい。畳み込みを待っているものは何もない:
一時的な失敗はログに残して後の同期に任せ、壊れた入力や新しすぎる入力は、ほかのクラウドファイルと同じく報告する。

**どうやって。** ほかのベースに支配されていないすべてのベースと、そのどれにも覆われていない一覧上のすべての差分を
検証し、`ReduceSql` で新しいベースに畳み込む。ベースは**決してローカルのデータベースから作らない**: ローカルの
マージは、ガードが拒否する行（main が別の id で同じ URL を持つフィード、main にフィードが無い記事など）を飛ばすので、
そこから作ったベースは、ほかのすべての端末からその行を
黙って落としてしまう。新しいベースの名前は `ks-<gen>-b-<dev>-<n>-<createdAt>-<hash12>` で、`n` はこの端末の一覧上で
最大のベースの番号に 1 を足したもの。`ks_vector` は入力ベースのベクトルを合わせ、それを畳み込んだ差分のうち隙間なく
続くものの分だけ伸ばす——**ただしベース自身の作成時刻より `KS_DELTA_GRACE_MS` 以上前に作られた差分だけを数える**
（`ks_covered.created_at` をベースの `ks_meta.created_at` と比べる。読む側がベクトルの含意を判断するときと同じ基準時刻）。
そのうえで `ks_covered` から差分の名前を外すのは、伸ばしたベクトルがそれを含意し、かつその差分がその基準時刻
以前に作られたと分かっている（`ks_covered.created_at`）ときだけで——2 つ以上畳み込んだ `(device, seq)` のコピーは
決して外さない——それ以外の名前はすべて残す（`TransportFiles.finalizeBase`）。入力ベースのベクトルがすでにその
`(device, seq)` に届いていても（複製が遅れて書いた重複など）、それより若い名前は残る: 新しいベースのベクトルは
それを含意しないので、名前がなければ、畳み込んだ差分をどちらの規則でも覆わないベースになってしまう。この年齢の規則が、ベクトルを信頼してよい根拠である: 含意された
`(device, seq)` の重複のうち、ベースの基準時刻より後に作られたものは含意されない（「転送用スキーマ」参照）ので、
畳み込まれずに含意されるには、重複がその基準時刻より前に作られ、猶予期間のあいだずっと、どの一覧にも見えないままで
いなければならない——[known-issues.ja.md](known-issues.ja.md) の「差分同期は、差分の古さを書いた端末の時計で測る」
参照。世代の最初のベース（`b-<dev>-1`、「参加」）のベクトル `{dev: 1}` は、伸ばすのではなく直接書くが、同じ規則で
読まれる: 基準時刻より後に作られたその番号の差分ファイルを含意することはない。新しいベースは `create` でアップロードする。入力が 1 つでも検証に失敗すれば、ベースは作らない。

**ガベージコレクション**は「どの変更も到達不能にしない」を保つ:

- 差分を削除してよいのは、それを覆うベースが存在し（直前に `metadata` で確認する）、差分自身の作成から
  `KS_DELTA_GRACE_MS`（7 日）以上たっているときだけ——作成時刻はその `ks_covered.created_at`、ベクトルが含意する
  差分なら名前の作成時刻（`BaseCoverage.coveredBefore`）——1 週間以内に同期する端末は、ベースをダウンロード
  せずに差分だけで追いつける。（ベースの古さではなく差分自身の古さで測る: 活発なアカウントではベースが週に何度も
  作り直されるので、ベースの古さの規則では差分がいつまでも消せない。）
- ベースを削除してよいのは、ほかのベースがそれを厳密に支配している間だけ（直前に `metadata` で確認する）:
  作成が同じか後であること（相手のベクトルが、こちらのベクトルの含意するものをすべて含意する）、すべての成分で
  以上のベクトル、それが明示的に挙げる差分をすべて相手も覆うこと——それが挙げる複製のコピーは、相手も含意では
  なく明示的に挙げていなければならない——、相手が名前で挙げる `(device, seq)` のうち、こちらのベクトルが含意するものは
  こちらも名前で挙げていること（seq を名前で挙げたベースのベクトルはその他のコピーを含意しなくなるので、こちらが
  そこで含意するコピーが覆われなくなる）、そして、より多くを覆うか、覆う範囲が等しければ作成が新しいか、作成時刻も
  等しければ名前が大きいこと。したがって 2 台が互いのベースを消し合うことはない。

**新しい端末のコスト。** ベース 1 つ（差分同期以前のデータベースファイルとほぼ同じ大きさ）と、閾値未満の差分。
ベースが覆う差分はダウンロードしない。参加にかかる量は、以前の最大でも約 1.25 倍である。

### 参加・リセット・接続解除

- **参加**（接続、プロバイダーの切り替え、世代の変化、複製の検出）: 新しい `ks_device_id` を発行し、カーソル、
  `sync_applied`、`ks_feed_folder_raw`、outbox、`ks_attempt` を消し、同じトランザクションで `sync_capture = (enabled 1, full_pending 1)`
  にするので、以後のすべての書き込みが記録される。そのうえですべてを受信し、全量送信を行う。結果は、差分同期以前の
  「マージしてからデータベース全体をアップロード」と同じになる。
- **最初の端末**は新しい世代に参加し、全量送信を最初のベースとしてアップロードしてから、ポインタを作る（`create`）
  ——したがってポインタが見えるときには、必ずそのベースが存在する。そのベース `b-<dev>-1` は、その番号の差分
  ファイルを一度も作らずに、ベクトル（`ks_vector = {dev: 1}`）でその端末自身の差分 `1` を覆う。したがって、どの
  ベースも、それが覆う差分を畳み込んだものであり続ける。ポインタの作成で競合して負けた端末は、次の同期で世代の
  違いに気づいて再参加する。送ったベースがポインタから指されることはない。
- **リセット**（`resetCloudData()`。使えなくなったクラウドデータからの回復）: 新しい世代に参加し、ローカルの全状態を
  そのベースとして（最初の端末と同じく）アップロードしてから、リビジョンチェック付きでポインタを置き換える。リビジョンが合わない
  （別の端末が先にリセットした）場合は中止し、ポインタを読み直す。古い世代のファイルは退避としてそのまま残す。
  ほかのすべての端末は新しい世代を見て再参加し、自分の全状態を送るので、ほかの端末にしかなかったデータも戻って
  くる——以前、ほかの端末が作り直されたファイルをマージしていたのと同じである。ポインタを置き換えた後、スタブで
  ない差分同期以前の `keryx.db.gz` は退避してスタブに置き換える（「クラウドデータのリセット（退避）」を参照）。
- **接続解除・切り替え**（`clearSyncFailureState()`、同じ mutex の内側）: `sync_capture.enabled = 0`（ローカル
  のみで使う間は何も記録しない）にし、`ks_*` キー、outbox、`sync_applied`、カーソル、`ks_feed_folder_raw`、
  保存中のファイルすべて（手順 0 の best effort の掃除）を消す。`ks_search_pending` と `ks_search_awaiting_body` は残す——ローカルの検索索引のものだからである。
  `ks_feed_folder_raw` を `sync_applied` と一緒に消すのは、これがこの端末がマージしたファイルのうちどの生の版が
  各フィードのフォルダーで勝ったかを表すものであり、新しい世代のファイルは改めて比べる——この端末自身の全量送信が
  持つ値（main の解決後の値）と比べる。ほかの端末の畳み込みが比べるのと同じである——からである。

### クラウドファイルの検証

ダウンロードした差分・ベース・差分同期以前のデータベースは、どれも、マージの前にこの検査を順に通る——畳み込みの
入力も同じ。1 つでも失敗すれば、その同期では何もマージしない。検査は一時ファイルに対して読み取り専用で行う。

| # | 検査 | 失敗したとき |
| --- | --- | --- |
| 1 | 名前がパターンに合う | 自分たちのものではない——無視する |
| 2 | ダウンロードが完了する | 一時的な失敗。次の同期で再試行する |
| 3 | gzip が展開できる（`MAX_SYNC_DB_SIZE_BYTES` が上限）、SQLite ヘッダ、名前のハッシュ（差分同期以前のデータベースは名前にハッシュを持たない） | どれかが失敗 → 同じ同期の中でもう 1 回ダウンロードする。それでも失敗 → 壊れている |
| 4 | `user_version` | このビルドより新しい → `SchemaVersionException`（`keryx.db.gz` では、`user_version` 1000 の空のファイルはスタブであり、この確認の前に見分ける。それ以外の新しいバージョン——テーブルを含む 1000 も——はこの失敗） |
| 5 | そのバージョンで期待される表と列（`TransportSchema`。差分同期以前のデータベースは `MergeSchema`）。転送ファイルでは、期待される表の列が期待どおりと完全に一致しなければならない: 列を追加する書き手は転送用バージョンを上げるので、同じバージョンで余分な列があるのは壊れたファイルであり、そのままだと折りたたみが黙って捨ててしまう。差分同期以前のデータベースは端末固有の列（`search_text` など）を持つ完全なローカルデータベースなので、足りない列だけを調べる。期待値に名前のない表は許す | 足りない（転送ファイルでは余分な列も）→ 壊れている。そのバージョンの期待値が未登録 → 判定できないので一時的な失敗として扱う（リセットは決して提案しない） |
| 6 | 古いバージョンはマイグレーションで上げる（`TransportSchema` のマイグレーション。差分同期以前のデータベースは `KeryxDatabase.Schema.migrate`） | マイグレーション中の SQLite エラー → 壊れている |
| 7 | 型と値の範囲を、期待スキーマから生成したクエリで調べる: id は空でない text、スタンプは integer か NULL、真偽値は 0 か 1、NOT NULL の列に NULL がない | 違反する行が 1 つでもあれば → 壊れている |
| 8 | `ks_meta`（世代・種別・端末・番号・作成時刻）がファイル名と一致する。ベースでは `ks_vector` / `ks_covered` の型 | 壊れている |
| 9 | 参照が閉じている: すべてのフィードのフォルダー、すべての記事のフィード、すべての `feed_tags` の行のタグとフィードが同じファイル内にある | 壊れている |

「壊れている」は `CloudDataIncompatibleException` で、扱いはこれまでと同じ: 自動同期を停止し、通知センターが
リセット（新しい世代）を提案する。すべての端末が自分の全状態を送り直すので、書いた端末がまだ存在する限り、壊れた
ファイルの内容もリセットで回復する。壊れたファイルを飛ばすことは決してない: 飛ばせば、その変更が黙って失われる。

検査 7 があるのは、SQLite が列の型を強制しないためである。スタンプの列にテキストの値があると、どの数値よりも
大きいと比較されるので、以後の後勝ちの比較にすべて勝ってしまう——さらにローカルのデータベースに入ると、生成された
SQLDelight コードの `getLong` がそれを読むときに例外を投げ、アプリがクラッシュする。差分同期以前のデータベースにも
適用する（以前のマージはこれを検査していなかった）。

検証とマージの失敗は `DatabaseMerger` / `SyncRepository` の内側で分類し、`Result.Err`
（`CloudDataIncompatibleException`、`SchemaVersionException`、または一時的な `CloudStorageException`）として
返す。外へ伝わるのは `CancellationException` だけである。検証で捉えられないのは、形式は正しいのに内容が論理的に
誤っているファイル——書いた端末の不具合——である。ハッシュが証明するのは、ファイルがアップロードされたものと
同じであることだけである。

### デバウンス

ローカルの変更がどれだけの頻度で同期を起こすかが、差分ファイルがいくつ書かれるかを決める。そこで `SyncScheduler` は
2 種類の待ち時間を持つ（どちらも最後の変更から計測し、連続した変更は 1 回の同期にまとまる）。

- **構成の変更**（購読・購読解除、名前変更、フォルダ、タグ、グローバル設定、単一フィードの更新）は
  `scheduleSync()` を呼び、`SYNC_DEBOUNCE_MS`（5 秒）後に同期する。
- **読書状態の変更**（既読・未読、スター、すべて既読）は読み進めるあいだ 1 件ずつ発生するため
  `scheduleDeferredSync()` を呼び、代わりに `DEFERRED_SYNC_DEBOUNCE_MS`（5 分）の静止を待つ。その間に構成の
  変更が来れば待ち時間は 5 秒に縮まり、読書状態の変更も一緒に送られる。
- `SyncRepository.flushPendingSync()` は保留中の変更があれば即座に同期する。アプリがフォアグラウンドを
  離れるときに呼ばれる: Android の `MainActivity.onStop`（構成変更時は除く）、iOS のシーンがバックグラウンドに
  入ったとき（バックグラウンドタスク内で）、デスクトップのウィンドウをトレイへ隠したとき（Compose デスクトップも
  ネイティブ macOS アプリも）。デスクトップアプリの終了時はこのためにネットワークを待たない。保留分は次回起動時の
  同期で送られる。実行中の同期があればまずその完了を待つ（その同期は開始時に保留フラグを下ろして
  いるため）。呼び出し側のバックグラウンド猶予が、そのアップロードも含めて守られる。
  それより前に、呼び出し元のスレッドの外でまだキューに残っているローカル書き込み（既読・未読やスターの変更、グローバル
  設定の変更、フィードの購読解除・移動などのフィードリスト操作。`PendingLocalWrites` で数える）を、最大
  `LOCAL_WRITES_FLUSH_WAIT_MS`（10 秒）待つ。こうした書き込みは実行されて初めて同期を予約するため、離脱の
  直前に行った変更は、待たなければまだ保留として見えない。
- Android と iOS では `flushOnLeavingForeground()` 経由で呼ぶ。アプリ自身が起こした離脱は対象外にする:
  `BrowserOpener` が起動時に印（`ExternalAppLaunch`）を付け、次の離脱がその印を消費するので、ブラウザで記事を
  読んでも記事 1 件ごとに差分を書くことはない。アプリが前面に戻るたびに印は消す。変更は
  長い窓、次の同期、または次の本当の離脱まで保留のまま残る。
- 先に走った同期（更新サイクルの同期、手動同期）も保留中の変更を拾う: 「未同期の変更あり」フラグは同期の開始時に
  下ろされ（その差分に含まれるため）、成功以外のあらゆる終わり方——エラー結果、例外、キャンセル
  （iOS はバックグラウンド化時に更新サイクルの同期をキャンセルする）——で立て直される。フラグが下りた状態で
  満了したデバウンスは何もしない。
- フィード更新そのもの（`FeedRepository.refreshFeeds`。必ず `RefreshCycleRunner` のサイクル内で実行される）は
  同期を予約しない。更新→同期のサイクルは直後に同期する。起動時の同期→更新のサイクルは更新の後に何も続かない
  ため、更新が書いた内容のために短い窓の同期を 1 回予約する（`scheduleSync()`）。
- 状態が変わらない既読・未読やスターの呼び出し（既読の記事を開き直すなど）は何も書かず、同期も予約しない:
  単一行の更新は状態が変わるときだけ書くようガードされ、`read_at` / `starred_at` は本当の変更でのみ打刻される。
  そのため後勝ちでも、記事を開き直しただけで他端末の後からの「未読に戻す」に勝つことはなく、未読のまま残る。

変更を遅らせても、それを送るはずだった同期が失敗・キャンセルされても失われることはない: 種類を問わず次の同期が outbox の中にそれを見つける（前述の
「送信」参照）。変わるのは他のデバイスに届くまでの時間だけである。

### 同期の進捗表示

`SyncRepository` は `syncPhase: StateFlow<SyncPhase>`（`IDLE` / `CHECKING` / `DOWNLOADING` / `MERGING` /
`INDEXING` / `PREPARING` / `UPLOADING` / `ARCHIVING`）を公開しており、クラウド同期設定タブは「同期中かどうか」
（`ActivityCenter.activity` のスナップショットの `syncing`、単なる真偽値）だけでなく「今どの段階か」を表示できる。すべての遷移は
`sync()`/`resetCloudData()` が保持しているのと同じ `mutex` の内側で行われるため、後から並んだ同期が前の同期の
古いフェーズを見てしまうことはなく、そのロック内側の `finally` が常に `IDLE` に戻す — 成功・分類済みの
`Result.Err`・捕捉されない例外のいずれの経路でも。

各フェーズは上記の各ステップに対応する：`CHECKING` はポインタとスタブの `metadata()` 呼び出しと一覧取得
（手順 1〜2）、`DOWNLOADING` はクラウドファイルの取得（受信と、畳み込みの入力）、`MERGING` は検証・畳み込み・
`DatabaseMerger.merge()`、`INDEXING` は `search_text` の再計算と `ftsManager.indexMissing()`、`PREPARING` は差分や
ベースの作成（`DeltaExporter`、`ReduceSql`、圧縮）、`UPLOADING` は `create` 呼び出しとポインタ・スタブの置き換え。
`resetCloudData()` は新しい世代のベースのために `PREPARING` / `UPLOADING` を通る。`ARCHIVING` は、差分同期以前の
ファイルを退避し、その場所にスタブを置いている間に使う。

`autoSyncSuspended` によってスキップされる `AUTOMATIC` 同期は `trackSync` に一切入らないため（後述の「自動同期の
抑制」参照）、その（一瞬の）実行中ずっと `syncPhase` は `IDLE` のまま — このスキップが同期スピナーを回さないのと
整合している。バイト単位の進捗（ダウンロード／アップロード済みバイト数の割合）はどのフェーズにも存在しない —
`CloudStorage` の `download`/`upload`/`create` は進捗コールバックを受け取らないため、3プロバイダすべてに渡って
このインターフェースを変更しない限り、フェーズ単位が得られる最も細かい粒度になる。

### 自動同期の抑制

`SyncRepository.sync(trigger: SyncTrigger = MANUAL)` は「誰が呼んでいるか」を受け取る。
`SyncTrigger.AUTOMATIC`（デバウンス書き込みの消費者、`runStartupMaintenance`（デスクトップの
`StartupTasks.kt`、Android の起動経路、Apple SDK の `KeryxSdk` で共有）、`backgroundUpdateLoop`
（`domain/BackgroundRefreshLoop.kt`。デスクトップの `main.kt` と Apple SDK の `KeryxSdk` が実行する）、Android の `FeedRefreshWorker` と `DeferredSyncWorker`）はゲートの対象になる —
`autoSyncSuspended`（`StateFlow<Boolean>`）が true の間、`AUTOMATIC` 呼び出しは
ダウンロード／マージ／アップロードのサイクルを一切実行せず `Result.Ok(Unit)` を返す。同期スピナーも
動かさず、通知センターにも触れないので、既に利用不能と分かっているクラウド DB が書き込みのたびに
再ダウンロード・再マージされることはない。`SyncTrigger.MANUAL`（デフォルト。UI から呼ばれる同期
——ツールバー／メニューの「今すぐ同期」、「すべて更新」、初回接続時の同期は `SettingsViewModel.connect()`
と `SetupViewModel` のどちらも——はすべてこちら）は**常に実際に実行される**。ユーザーが明示的に同期を求めた場合、必ず本当の試行と
その失敗理由を受け取れる — 黙って何もしない、ということは起きない。

ゲートは `updateAutoSyncGate`（`sync()` と `resetCloudData()` の両方から、`emitErrorNotification` の
直前に呼ばれる）が設定する: 結果が `CloudDataIncompatibleException` を運んでいれば true に、
`Result.Ok` ならどんな場合でも false にクリアする。`SchemaVersionException` は意図的に除外している
——同じく永続的だが、その直し方は「アプリを更新する」であり、これでバックグラウンド同期をゲートすると、
新しいバージョンが導入されて動き始めた瞬間が隠れてしまう。`scheduleSync()` もデバウンス信号を積む前に
ゲートを確認するので、クラウドが利用不能と分かっている間は書き込みバーストがデバウンス待ちのループすら
起動しない。

`autoSyncSuspended` はあえて**インメモリで、永続化しない**: プロセス再起動は「他端末がクラウドの
データを直しているかもしれない」を確認できる無料の再試行であり、ゲートの本来の目的
——同じ壊れたファイルを1プロセス内で何度も再ダウンロード・再マージせず、同じ通知を何度も出さないこと
——にはそれ以上の永続性は不要である。成功した同期（手動・自動どちらでも）、`resetCloudData()` の成功、
そして `clearSyncFailureState()`（ミラーされている失敗理由のテキストも合わせてクリアする。接続の
解除・切り替え時（`SettingsViewModel.disconnect()`/`switchTo()`）に呼ばれる）でクリアされる。

リセット／通知の UI 側はゲートの影響を一切受けない: 通知センターの `ResetCloudData` ボタンも設定画面の
リセットボタンも無条件（ゲートされない）で、スキップされた `AUTOMATIC` 呼び出しは `lastSyncError` に
一切触れないため、クラウド同期タブは同期が今なぜ壊れているかを表示し続ける。

### ネットワークゲート（従量制回線とデータセーバー）

上記と並んで、`AUTOMATIC` だけに効く 2 つ目のゲートがある。差分は小さいが、同期はなお大きな
ファイル——参加時の全量送信、追いつくためのベース、畳み込み——を動かしうるので、携帯端末での自動同期は、同期の
たびにデータベース全体をアップロードしていた頃と同じく、既定では従量制でない回線を待つ。OS は
`platform/NetworkConditionMonitor`（`platformNetworkConditionMonitor()` expect から得るインターフェイスで、
`core/NetworkCondition(metered, dataSaver)` の Flow を流す）を通じて 2 つのシグナルを返す: 現在の回線が
**従量制**か（Android: デフォルトネットワークに `NET_CAPABILITY_NOT_METERED` がない — モバイル回線、テザリング、ユーザーが従量制に設定した Wi-Fi。iOS:
`nw_path_is_expensive` — モバイル回線または Personal Hotspot）と、ユーザーが OS の
**データ節約モード**をオンにしているか（Android: データセーバー、つまり
`restrictBackgroundStatus == ENABLED`。Android は従量制回線にしか適用しない。iOS: 低データモード、
`nw_path_is_constrained`。Wi-Fi を含むどの回線にも設定できる）。ネットワークがない状態は制限なしとして扱う。
デスクトップと macOS はどちらも報告せず（`supported = false`）、常に制限なし。

`domain/NetworkUsagePolicy` がそれを、すべての呼び出し元が共有する 1 つの判定にする:

| | 制限なし | 従量制 | データセーバー / 低データモード |
| --- | --- | --- | --- |
| 自動同期（`SyncTrigger.AUTOMATIC`） | 実行 | `syncOnMeteredNetwork` がオンでなければ保留 | 保留 |
| 自動フィード更新（`AUTOMATIC` の `RefreshCycleRunner` サイクル） | 実行 | 実行 | スキップ |
| 手動同期 / すべて更新 / プル更新（`MANUAL`） | 実行 | 実行 | 実行 |

`syncOnMeteredNetwork` は端末ローカルの設定（`local_settings.json`、既定はオフ）。`SyncRepository` は
ゲートを `automaticSyncAllowedFlow: () -> Flow<Boolean>` ラムダとして受け取る — `cloudProvider` と同じ理由で
遅延評価（`SettingsRepository` が `SyncRepository` を `SyncScheduler` として依存しているため）で、
`SharedModule` がモニターと設定を組み合わせて作る。

`sync(AUTOMATIC)` が回線を不許可と判定した場合（かつプロバイダ接続中）、`trackSync` には一切入らず
— スピナーもフェーズも通知もなく、`lastSyncError` も触らない — `Result.Ok(Unit)` を返すが、抑制ゲートと
違って保留中のものがあることを覚えておく: `syncDeferredForNetwork`（`StateFlow<Boolean>`）を立て、
アプリスコープ上の待機ジョブを 1 本だけ（その間に何回保留されても 1 本）起動し、ゲートの Flow が true に
なった瞬間に `scheduleSync()` を呼び、その時点でフラグを下ろす: 保留は終わっており、スケジュールされた
同期は実行されるか（失敗すれば通常どおり `lastSyncError` に出るので、フラグが実行されていない待機を
示すことはない）、デバウンス中に回線がまた制限側に戻れば再び保留される。成功した同期（手動を含む）も
フラグを下ろして待機ジョブを取り消す — ただし、その実行中に別の同期が保留された場合は除く（世代カウンタで
判定）。その保留は、成功した同期がアップロードしていない変更を対象とするため。自動同期の停止
（`autoSyncSuspended`）と `clearSyncFailureState()`（切断・切り替え）でも下ろし、切断と競合した保留は
フラグを立てない。

`autoSyncSuspended` と同じく、保留状態は**インメモリ**: 保留中の変更そのものは `sync_outbox` に
永続化されているので、次に許可された同期がその間の変更をすべて送る。待機ジョブは
プロセスが生きている間しか働かないため、Android では加えて保留した同期を、その同期が許可される回線（従量制回線での同期をユーザーが許可していなければ従量制でない回線）を条件とする
`WorkManager` ジョブに渡し、アプリを閉じた後でも同期されるようにしている（[background-update.ja.md](background-update.ja.md)
の「保留された同期」を参照）。iOS では、閉じたアプリが残した保留は、回線が許す次のバックグラウンド更新か
前面での同期で解消される。

自動フィード更新は、各取得が条件付きリクエストで通常は小さいため、従量制回線でも許可したままにしている。
止めるのは、ユーザーが明示的に通信の節約を求める OS のデータ節約モードだけ。

## マージ（`DatabaseMerger` + `MergeSql`）

畳み込んだ転送ファイル（または検証済みの差分同期以前のデータベース）を `cloud` としてアタッチし、テーブルごとに
マージする。転送ファイルは `DatabaseMerger.mergeTransport` を通る: `KeryxDatabase.Schema.migrate` は決して実行せず、
`user_version` を `TransportSchema.VERSION` と照らし（古いものは `TransportFiles.prepareForMerge` でマイグレーション
する）、下の分類のあいまいな `SQLITE_ERROR` の場合は `MergeSchema` ではなく転送用スキーマ（`TransportFiles.schemaMatches`）
と照合する。`merge` は移行のために差分同期以前の動作を残している。

> [!IMPORTANT]
> SQLDelight の JVM `JdbcSqliteDriver` はファイル DB に対してステートメントごとに新しいコネクションを開く。そのため `ATTACH` を driver 越しに実行すると、後続のマージ文から見えない（`no such table: cloud.*`）。マージは `platform/DatabaseMerger` の**専用の単一コネクション**で行う: attach → バージョン確認 → マージ（トランザクション）→ detach。

マージ SQL（`MergeSql`）の要点:

- **列は明示する。** さらに、転送用スキーマと、現行スキーマへ移行した差分同期以前のデータベースの両方にある列だけを
  使うので、1 つの文の集合で差分・ベース・移行のすべてを扱える。
- **同着は、すべての文で値によって決める。** 両側のスタンプが同じときは、正規化した値が大きいほうのグループが勝つ。
  正確には（`SyncLww`）、フィールドグループの各版に順位の行値 `(stamp IS NOT NULL, COALESCE(stamp, 0),
  c1 IS NOT NULL, COALESCE(c1, 0), c2 IS NOT NULL, COALESCE(c2, 0), …)` を与える。`c1, c2, …` はそのグループの
  すべての列——スタンプの列、続いて値の列——で、2 つの順位を SQLite の行値の `>`（BINARY 照合）で比べる。順位が厳密に
  大きいときだけ、その版がもう一方を置き換える。したがって、スタンプのある版はスタンプのない版に勝ち（NULL は
  「そのイベントがない」）、スタンプの大きいほうが勝ち、スタンプが同じなら値を列の順に比べて決める: NULL が最小、
  それ以外は SQLite 自身の順序（整数は数値順でテキストより小さく、テキストはバイト順）。どの要素も NULL にならない
  ので比較が NULL になることはなく、同一の版どうしが置き換え合うこともない。スタンプを 2 つ持つグループ（記事の保持
  グループ、後述）は、最初の 2 要素の代わりに `どちらかのスタンプ IS NOT NULL, MAX(COALESCE(s1, 0), COALESCE(s2, 0))`
  で順位を付ける。記事の本文グループは、これらすべての前に 2 つの要素を置く（後述）。差分同期以前の規則（「同着はクラウドが勝つ」）は、クラウドに 1 つのファイルしかなかったから収束していた。差分では
  端末ごとにファイルをマージする順序が違うので、どちら側かで決める規則だと、その順序が結果を決めてしまう。端末自身の
  書き込みは常に、その行がすでに持つスタンプより大きく打刻する（[db-schema.ja.md](db-schema.ja.md) の「設計方針」参照）
  ので、同着は 2 台が同じミリ秒に独立して書いたときにしか起きない。
- **`cloud` 内の重複は決定的に解決する。** 畳み込んだファイルは、同じ一意キー（`feeds.url`、
  `articles(feed_id, guid)`）を持つ行を、別々の端末から 2 つ持ちうる。そうしたキーで照合する
  文は、その中の勝者——`updated_at` が最大、次に id が最大——だけを対象にする。参照を id で解決する文
  （`mergeFeedFolderId`、`feedTags`）は、引き続きすべての行を見る。（タグとフォルダーの名前は一意キーではなくなった:
  id は作成時の名前から導かれるので、独立に作成された同名の行は同じ id に収束する。ただしリネームが交差すると、
  異なる id が同じ現在の名前を持つこともあり、UI が番号を振る。）
- **`cloud` に行が無いことは何も意味しない。** 差分は一部の行しか持たない。参照先の行によって結果が変わる文
  （`mergeFeedFolderId` の「フォルダーが `cloud` で生きていなければ NULL」、`feedTags` のタグ解決）も、これまでと同じ
  答えになる。どの差分も、自分の行が参照する行を含んでいるからである（検証の手順 9 で確認する）。
- feeds / tags / folders / global_settings: 後勝ち（論理削除を含む）。feeds の文の `ON CONFLICT` は内容系の
  フィールド（url / title / description / … + `updated_at`）だけを扱い、利用者が編集するフィールドはそれぞれの
  スタンプを使う専用の文でマージする: `mergeFeedFolderId`（`folder_id` / `folder_updated_at`）、
  `mergeFeedSortOrder`、`mergeFeedCustomTitle`、`mergeFeedDeletedAt`。`folder_id` は 3 分岐で解決する: クラウドが
  参照するフォルダーが `cloud.folders` で生きていなければ NULL、そのフォルダーが `main` で生きていればクラウドの
  `folder_id`、それ以外は NULL。（フォルダーの id は名前から導かれるので、同じフォルダーはどの端末でも同じ id となり、
  同名検索はもう残っていない。）
  保存される `folder_id` は解決後の値——この端末の id で、勝ったファイルが持っていた id とは限らない——なので、
  マージはクラウドの生の `folder_id` をそれと比べない: `folder_updated_at` が等しいとき、2 つの id は別々の id 空間に
  属し、マージの順序が結果を決めてしまう（一方 `ReduceSql` の畳み込みは生の最大値を残す）。勝った生の版を
  `ks_feed_folder_raw` に並べて保持し、フォルダーのマージは 3 つの文で行う: フィードの生の行が無いか、そのスタンプが
  main のものでない（その後ローカルで移動した——ローカルのフォルダーの書き込みはすべて `MAX(now, previous + 1)` で
  打刻するので、古くなった行が main のスタンプを持つことはない）ときは main 自身の値で置き直す。生の行より順位が
  高いクラウドの版を、上の解決で適用する。同じ比較でクラウドの版を生の行に記録する。こうして、どのマージの順序でも
  どの畳み込みでも、同じ生の勝者が選ばれる。フィードの取得状態（`feed_fetch_state`）は端末ローカルで、マージしない。
  feeds は **`id`** で照合する。id は `url` から **UUIDv5** で決定的に生成する（`IdGenerator.feedId`）ので、同じ
  フィードはどの端末でも同じ id になる。
- **tags / folders: フィールドごとの後勝ち。** feeds と同じく、名前（`name_updated_at`）、色（`color_updated_at`、
  tags のみ）、並び順（`sort_order_updated_at`）を、それぞれのスタンプで決める。`updated_at` は作成・削除・再有効化を
  打刻する。2 台が同じタグの別々のフィールドを変えれば、両方の変更が残る。行は **id だけで**照合する——タグや
  フォルダーの id は作成時の名前から導かれる（`IdGenerator.tagId` / `IdGenerator.folderId`。v2→v3 移行が既存の行を
  一度だけ振り直した）ので、2 台が同じ名前を独立に作れば、通常のフィールドごとのマージで 1 行に収束する。id が
  main に無い行はそのまま挿入する: main が別の id で持つ名前（2 つのリネームが 1 つの名前に着地した場合）は
  そのまま通し、同名の行は共存する（UI が番号を振る）。名前由来 id の意図された帰結のひとつは、feeds の「同じ URL は
  同じフィード」と同じく、片方の端末でリネームしたタグを、最初の同期の前に別の端末がその元の名前で新規作成しても、
  マージ後は 1 行であり、名前は `name_updated_at` で決まる——名前を作った端末は、それがリネーム後の名前に変わるのを
  見ることがある（片方の端末で「Work」を「Job」にリネーム、もう片方で「Work」を作成: どの端末でも「Job」という
  1 つのタグになる）。
- **v2 の identity の再統合（すべてのマージ）。** v2→v3 移行で振り直されたタグやフォルダーは、移行前の id を
  `v2_id` に保つ（移行後に作られた行では NULL）。v2 の id を共有していた 2 台が、アップグレード前にその行を別々の
  名前にリネームしていると、それぞれ異なる名前由来 id を導き、id だけの照合では両方が残ってしまう。`MergeSql` は
  フィールドごとのマージの前に、すべてのマージ（差分・ベース・差分同期以前）で、`v2_id` が非 NULL のクラウド行に
  ついて次を行う:
  1. グループはその `v2_id` を共有するクラウド行で、正規のクラウド行は `updated_at` が最大、次に id が最大の行。
  2. 対象 id は、main に同じ `v2_id` を持つ行があればその id（その同一性はこの端末ですでに確立している）、
     無ければ正規のクラウド行の id。
  3. `cloud` に対象行が無ければコピーして入れ、フィールドごとの文が同一性ごとに 1 行を id で照合できるようにする。
  4. 子の参照（`cloud.feeds.folder_id`、および `cloud.feed_tags.tag_id`——リンクは先に `(feed_id, tag_id)` ごとに
     通常の後勝ちで 1 本に畳む）を対象 id へ移し、移し替えた行を削除する。
  外部キー安全な順序で、正規行とリンクの選び方は畳み込み順に依存せず、2 度実行しても何も変わらない。transport
  ファイルが `v2_id` を運ぶので差分・base でも効き、差分同期以前のファイルは同じ移行で `v2_id` を得る。
  マージは `ks_id_remap` を参照しない。
- articles は 3 つのグループ:
  - **本文** — `content`・`summary`・`title`・`url`・`author`・`published_at`・`thumbnail_url`（と、ローカルの
    マージが既存の行では書き換えない `feed_id` / `guid`）で、スタンプは `body_updated_at`。スタンプを比べる前に、
    `content` を持つ版は持たない版より上、何らかの本文（`content` か `summary`）を持つ版は持たない版より上に置く。
    そのあと `body_updated_at`、そのあと値で決める。したがって `content` は実質 OR マージになり、要約が本文を
    置き換えることも、軽い行（`content` / `summary` が NULL）が本文を消すこともなく、タイトル・URL・著者などは
    常に本文と同じ版から取られる。記事が `content` を持てば `summary` は NULL にする。`body_updated_at` は本文の
    列が変わったときだけ進み（変わらない記事を書き直すだけのフィード更新では進まない）、既読・スター・削除では
    進まない——記事を開いただけの端末が、自分の古い本文で別の端末の新しい本文に勝つことはない。
  - **既読** — `is_read` を `read_at` で決める。
  - **保持** — `is_starred`・`starred_at`・`deleted_at`・`deleted_updated_at` を 1 つのグループとし、
    `MAX(COALESCE(starred_at, 0), COALESCE(deleted_updated_at, 0))` で順位を付ける: **新しいほうの操作が勝ち**、
    グループ全体をその操作を持つ版から取る。スターはローカルで削除を取り消し（`updateStarStatus`）、スターも
    キャッシュ削除も行の両方のスタンプより大きく打刻するので、最も新しいイベントが常にそのグループに勝つ。（以前の
    規則——スターと削除を別々のグループにし、さらに「削除より新しいスターは記事を復活させる」——は可換ではなかった:
    削除、それより新しいスター、さらに新しいスター解除を別々の順序でマージすると、結果が食い違った。）その結果、
    別の端末のスターで復活し、そのあとスターを外された記事は、次のキャッシュ削除で再び削除されるまで表示されたままになる。

  `cached_at` と `updated_at` は新しいほうを取り（`updated_at` は行の汎用のスタンプで、どのグループのキーでもない）、
  `created_at` は古いほうを取る。`search_text` はマージしない: マージが本文を埋めた、または変えた記事は `ks_search_pending` に
  登録し、新しく挿入された記事は `''` から始まり、本文なしで挿入された記事は `ks_search_awaiting_body` に記録する
  （「FTS5 の扱い」参照）。articles は **`id`**（`(feed_id, guid)` の
  UUIDv5、`IdGenerator.articleId`）で照合する。
- feed_tags: 後勝ち。フィードとタグが main にあるとき（どちらも id で。タグの id は名前から導かれるので、同じタグは
  どの端末でも同じ id になる）だけ取り込む。main がタグをまるごと持たないリンクは孤児なので飛ばす。main が墓標として
  しか持っていないタグへのリンクは、ほかの行と同じく取り込む——リンクは自分の `updated_at` に乗る。
- `NOT EXISTS` / `EXISTS` のガードは、main と衝突する行（別の ID で同じ URL や `(feed_id, guid)` を持つ行、main が
  持たない参照先の行）を飛ばすので、UNIQUE / FK 違反でトランザクション全体が失敗することはない。タグとフォルダーの
  行には追加のガードはない: 別の id が同じ名前を持っていても通し、同名の行は共存する。
- `MergeSql.all` の順序: folders（id ごとのフィールド文、次に insert）、feeds、フォルダーのマージの 3 つの文と残り
  3 つの `mergeFeed*`、tags（フィールドごと、insert）、articles、feed_tags、global_settings。folders は feeds より前
  （`feeds.folder_id` のため）、`mergeFeed*` はその両方の後。
- 管理用の表（`sync_outbox`、`ks_search_pending`、`ks_feed_folder_raw`、`sync_merging` など）は主キー以外の制約を
  持たないので、後述の分類が前提とする
  「main が既存の状態で違反しうるのは FOREIGN KEY 制約だけ」は引き続き成り立つ。

`ReduceSql` は、同じフィールドごとの規則と同着の決め方で、転送ファイルを 1 つに畳み込む。キーは主キーだけで、
ローカル用のガードは持たない——それは各端末自身のマージの役目である。

### マージ失敗の分類

`DatabaseMerger.merge` は、`mergeUnclassified`（分類前の実装本体、private）からの失敗を SQLite の
**エラーコード**（ロケールや JDBC ドライバのバージョンに左右されやすいメッセージ文字列ではない）を使って分類する。
エラーコードは、cause チェーンを辿って `org.sqlite.SQLiteException` を探すことで得る（`findSqliteCause`、
cause の循環に備えて深さ上限あり）。`SchemaVersionException` は、分類する catch-all よりも**先に** catch して
再 throw する — これにより誤って再分類されることはない。分類は意図的に保守的で、認識できないエラー
（cause チェーンに `SQLiteException` が無い場合を含む）はそのまま再 throw される。そのため分類漏れが
挙動を後退させることはなく、`SyncRepository` 自身の catch-all が一時的な `CloudStorageException` として
扱う。

2 層の分担は次のとおり: デスクトップの `actual` が担うのは `resultCode.code and 0xFF` をドライバ非依存の
`SqliteFailureCategory`（`CORRUPT` / `CONSTRAINT` / `STATEMENT_ERROR` / `OTHER`）へ落とすこと、下表に必要な
判断材料を集めること、判定結果のログ出力だけ。下表の判定ロジック本体は `commonMain` の
`domain/MergeFailureClassifier.classify` にあり、（カテゴリ、エラーコード名、ローカルの外部キー判定、遅延評価される
`validateSchema` コールバック、遅延評価されるクラウド整合性コールバック）から `CloudDataIncompatibleException` または
`null`（= 元の失敗をそのまま再 throw）を返す純粋関数である。どちらのコールバックもダウンロード済みファイルを開き直す
ため、`validateSchema` は曖昧な `STATEMENT_ERROR` の場合にのみ、クラウド整合性は `CORRUPT` の場合にのみ呼ばれる。分類そのものにプラットフォーム固有の要素は無いので、数値エラーコードを公開しないドライバ
（Android の `android.database.sqlite.SQLiteException`）を持つターゲットでも、同じカテゴリを与えるだけで済む。

Apple の `actual`（`DatabaseMerger.apple.kt`）も同じ対応付けと同じ `MergeFailureClassifier` を使うが、コードの
見つけ方が異なる。cause チェーンを（同じく深さ上限付きで）辿り、次の 2 種類の例外のどちらかを探す：
`platform/RawSqliteConnection.kt`（マージ専用の接続）が投げる自前の `SqliteException`（エラーコードを直接持つ）、
または、クラウドファイルを開いてマイグレーションする間に `NativeSqliteDriver` が投げる SQLiter の
`SQLiteExceptionErrorCode`。SQLiter は生の `errorCode` を private にしているため、読める値は `errorType.code`
（主コードのみ）だけである。この getter は SQLiter に enum の項目が無いコードに対しては例外を投げるので、その場合は
「コードが見つからない」（そのまま再 throw）として扱う。

ATTACH する前に、Apple の `migrateCloudIfOlder` は古いクラウドファイルを `NativeSqliteDriver` でロールバック
ジャーナルモードのまま開き、ローカルのスキーマまで上げる。このドライバはファイルを最初の文で遅延して開く
（つまりそこでマイグレーションする）——`DatabaseDriverFactory.apple.kt` が生成時に 1 文実行するのと同じ理由——ため、
ドライバを閉じる前に些細な `SELECT 1` を実行し、その後ファイルの `user_version` を読み直して、まだローカルの
スキーマバージョンでなければ `IllegalStateException` を投げる。この例外は意図的に SQLite のエラーコードを
持たないので、マージはこれを未分類（一時的）のままにする：何もせずに終わったマイグレーションはアプリ側の
不具合かもしれず、破壊的なクラウドデータのリセットで応じてはならない。

| SQLite の主エラーコード | 分類 |
| --- | --- |
| `SQLITE_NOTADB`、`SQLITE_CORRUPT`、`SQLITE_FORMAT`、`SQLITE_EMPTY` | **クラウドファイルが壊れていると確かめられたときだけ永続。** ロールバックの後、ダウンロードしたクラウドファイル（他から書き込まれない一時ファイル）を作成せずに開き、`PRAGMA quick_check` で調べる：問題が報告される、または開くか調べるときに `SQLITE_NOTADB`／`SQLITE_CORRUPT` で失敗する → `CloudDataIncompatibleException`。`ok` → 壊れているのは*ローカル*の DB なので、そのまま再 throw。それ以外（判定不能）→ そのまま再 throw。したがってローカル DB の破損にクラウドデータのリセットで応じることはない。 |
| `SQLITE_CONSTRAINT`（`_UNIQUE`／`_NOTNULL`／`_FOREIGNKEY` 等、全ての拡張 `SQLITE_CONSTRAINT_*` を含む — 拡張コードの下位バイトは常にその主コードに一致する） | ***main* が原因でないと確かめられたときだけ永続** → `CloudDataIncompatibleException`。`MergeSql` の `NOT EXISTS`/`EXISTS` ガード（前述）が main 側の行との衝突は既にすべて潰しており、UNIQUE／NOT NULL は main で常に強制されている。残るのは、クラウド DB 自身の行集合が制約に違反している場合（クラウド DB 内部の url 重複、クラウド側の（より緩い）スキーマが許していた NULL 等）と、**main に元からある外部キー違反**（外部キーを強制する前のデータや移行によるもの）を、文がその行を変更したときにマージの `PRAGMA foreign_keys=ON` が表に出す場合である。今の `MergeSql` が外部キー列に書くのは、main に存在すると保証された値か NULL だけで（`mergeFeedFolderId`）、親も削除しないので、これは今後追加される文への備えである。ドライバが拡張リザルトコードで UNIQUE・PRIMARY KEY・NOT NULL の違反と報告した失敗は、書き込みのたびに強制されている種類なので main の既存の状態が原因になり得ず、以下のチェックや再実行をせずにその場で分類する。再実行しても同じ判定にしかならず、マージの書き込みロックを長く持つだけだからである。desktop と Apple はこのコードを読めるが、Android の requery は公開していないので、Android は常に以下の全経路を通る（main が元から違反しうるのは外部キー制約だけで、スキーマに CHECK 制約やトリガーを足すときはこの判定を見直す必要がある）。以下はすべて、**失敗したマージのトランザクションがまだ開いているうちに**マージの接続で行うので、途中で他の書き込みが main を変えることはない（例: 再購読で孤立した記事の親が補われる）。(1) `PRAGMA main.foreign_key_check` の結果を V0 とする。それより前の文は外部キーの即時チェックを通っているので、V0 は main に元からあった違反である。V0 が空なら main は原因でない → `CloudDataIncompatibleException`。(2) そうでなければ、`PRAGMA defer_foreign_keys=ON` にして、失敗した文とそれ以降のすべての文（`MergeFailureClassifier.remainingStatements`）を同じトランザクションの中で再実行する。こうすると即時に失敗するのは外部キー以外の制約だけになる。失敗した文から続けても、最初からやり直すのと同じ状態になる — それより前の文は外部キーの即時チェックを通っており、制約違反は失敗した文自身の変更を取り消すためである。また Android ではこれしか方法がない。requery は `ROLLBACK` で始まる文をすべてトランザクション全体のロールバックとして扱うので、セーブポイントへの `ROLLBACK TO` を発行できないためである（理由は `MergeFailureClassifier.mainRuledOut` の KDoc にある）。再実行が制約違反で失敗した → クラウドの行による外部キー以外の制約違反 → `CloudDataIncompatibleException`。再実行が成功し、その後の `foreign_key_check`（V1）に V0 になかった行がある → クラウドの行が新しい外部キー違反を持ち込んだ → `CloudDataIncompatibleException`。再実行が成功し、V1 に新しい行がない → 失敗は元からある手元の違反によるもの → そのまま再 throw。それ以外（別の失敗、SQLite がトランザクションを既に終えていた、チェック自体の失敗）→ そのまま再 throw。どの場合もその後トランザクション全体をロールバックし、何もコミットしない。したがって手元の孤児行が、クラウド由来の制約違反を隠すことはない。クラウドファイルだけに触れる `migrateCloudIfOlder` で起きた制約違反は、構造上 main が原因になり得ないので分類する。 |
| `SQLITE_ERROR`（`no such table`／`no such column`） | **曖昧** — これは外部・レガシーなクラウドスキーマの見た目でもあり、（無関係なアプリのバグによる）ローカル側スキーマの破損の見た目でもある。ダウンロードしたクラウドファイルに対して `validateSchema` を呼んで解決する：`false` なら `CloudDataIncompatibleException`、`true` または `null`（判定不能）ならどちらもクラウド起因と確信できないためそのまま再 throw。 |
| それ以外（`SQLITE_CANTOPEN`、`SQLITE_IOERR`、`SQLITE_FULL`、`SQLITE_BUSY`、`SQLITE_LOCKED`、`SQLITE_READONLY`、`SQLiteException` が見つからない場合、等） | **一時的／アプリ側** — そのまま再 throw。 |

分類が `DatabaseMerger.merge`（`mergeUnclassified` だけをラップしており、呼び出し元がその後に行うことは
見えない）の内部に完全に閉じているため、`DeltaSync.mergeFolded` の post-commit の処理
——`ftsManager.indexMissing()` と `driver.notifyListeners(...)`。どちらもマージが**既に commit した後**に
走る——は構造的に見えない。ここでの失敗（例: ローカルの `articles_fts` テーブルが DROP されている、これも
`SQLITE_ERROR`）は `SyncRepository` 自身の catch-all で未分類のまま `CloudStorageException` として報告され、
`CloudDataIncompatibleException` には決してならない — マージ自体は既に成功しているので、そのために
破壊的なクラウドデータリセットを提示するのは誤りである。

マージのトランザクションがまだ開いているかの確かめ方は `actual` ごとに異なる。分かりやすいフラグは要求した状態を
記録するだけで、SQLite が自分で行ったロールバックを反映しないためである：デスクトップはマージのトランザクションに
ロールバックのリスナー（sqlite-jdbc の `SQLiteCommitListener` 経由の `sqlite3_rollback_hook`）を登録し、Apple は
`sqlite3_get_autocommit` に問い合わせ、Android はトランザクションとともに `SAVEPOINT` を開き、`RELEASE` が成功した
ことを、まだその中にいる証拠とする — 再実行の前に 1 回（続けて新しい `SAVEPOINT` を張るので、トランザクションが終わって
いれば何も再実行しない）、後に 1 回。再実行はトランザクションが開いていると確かめてから始めるので、どの文もトランザクションの
外で走って main にコミットされることはない。判定結果はその失敗そのものに対してだけ分類の段階へ渡され
（`MainRuledOutVerdict`）、チェック自体の失敗は suppressed として付け加え、元の失敗を置き換えることはない。

ダウンロードしたクラウド DB に対する `PRAGMA quick_check` は、失敗した経路でだけ、壊れているのがクラウドファイルか
ローカル DB かを見分けるために実行する（上の表を参照）。毎回の同期ではあえて実行しない — DB サイズに比例した
コストがかかるうえ、SQLite はマージが触れた瞬間に破損ページを別個のエラーコードとして返すので、マージが触れない
ページまで毎回全走査しても得られるものが無い。また、クラウド DB 自身のスキーマとしては整合していても、このアプリの
制約には違反するデータも検出できない（`quick_check` は DB が自分自身のスキーマと整合しているかしか見ない）。

## スキーマバージョン

関係するバージョンは 2 つある:

- **ローカルのスキーマ**（`keryx.db` の `PRAGMA user_version`、現在 3）。バージョン 3（`2.sqm`）は、同期の管理用の
  表とトリガーを追加し、`feeds` の取得状態を `feed_fetch_state` に移し、タグとフォルダーを作り直し（フィールドごとの
  スタンプの追加と `UNIQUE(name)` の廃止を 1 回の差し替えで行い、その間に子を退避・復帰させる。外部キーは有効のまま）、
  `articles.body_updated_at` を追加し（初期値はいずれも `updated_at`）、`search_text` が生の `content` / `summary` と同じままの記事（HTML 除去の導入前に
  書かれた行）を `ks_search_pending` に登録する。
- **転送用スキーマ**（各差分・ベースの `user_version`）。このビルドより古いファイルは、使う前に `TransportSchema` の
  マイグレーションで上げる。新しいファイルは `SchemaVersionException` を上げ、どのカーソルも進めずに同期を止める
  ので、アプリを更新すれば何も飛ばされない。

`.sqm` を追加するときは、転送用スキーマ（DDL、期待値、マイグレーション）、`MergeSchema`、記録用トリガーが比較する
列の一覧を一緒に更新しなければならず、食い違えばテストが失敗する。知らない列を無視することは決してしない: 古い端末が
その列なしで行を再送すると、新しい列が NULL で上書きされてしまう。同様に、そのバージョンが定義しない列を持つ転送ファイルは
（「クラウドファイルの検証」のチェック 5 で）壊れているものとして拒否し、その列を捨てたままマージしたり折りたたんだりはしない。

`DatabaseMerger.validateSchema` と転送ファイルの検証は、**null 許容**の判定を返す: そのバージョンの期待値が未登録の
場合や、検査自体が失敗した場合は `null`。`null` を「互換性なし」として扱うことは決してない——登録し忘れにすぎない
ものに対して破壊的なリセットを提案してはならない——ので、一時的な失敗として報告する。
`SyncMergerTest.validateSchemaReturnsTrueForValidKeryxDb` と、その転送用の対応テストが現在のバージョンを固定する。

## FTS5 の扱い

**ライブ DB の `articles_fts` は決して DROP しない。** 索引が端末の外に出ることはない: 転送ファイルは同期対象の
テーブルだけから作り、全量送信の `VACUUM INTO` コピーは読み取りにしか使わない。

索引の維持は 2 段構え:

- **hot path（フィード更新・同期マージ後）**: `FtsManager.indexMissing()` で未索引の新記事だけを増分投入
  （O(新着行)、索引を wipe しない）。全再構築（`'rebuild'`）は毎回だと O(索引テキスト総量) で重くスケールせず、
  実行中の検索を弾き得るため hot path では使わない。本文が更新された既存記事の索引は次の rebuild まで古いまま
  （許容。記事はなお旧トークンでヒットするので検索が 0 件に退行しない）。
- **マージ後の `search_text`。** `search_text` は同期しない。マージは、本文を埋めた、または変えたすべての記事を
  （マージのトランザクションの中で）`ks_search_pending` に登録し、新しく挿入された記事は `search_text = ''` から
  始まる。`search_text` の再計算は `indexMissing()` 自身が、書き込み用の mutex の中で、索引を作る前に行う。
  そのため、どの呼び出し元（マージ後、フィード更新・購読・インポート後、起動時）でも追いつく。`ks_search_pending` を
  rowid 順に 1 回だけ、バッチごとにたどる: バッチはトランザクションの外で読み、`HtmlText.toPlainText` で変換し、
  すべての文が書き込みである 1 つのトランザクションで書く。各行の更新は `content` と `summary` が読んだときのままで
  あることを条件とし、その更新が一致したときだけ行を `ks_search_pending` から外す。その間に別の書き手が本文を
  変えた行は次の呼び出しまで保留のまま残るので、古い本文から計算したテキストが保存されることはない。変換で
  例外が出た行は、残りを止めずに `''` にする（ログにも残す）。1 つのカーソル行で読むには長すぎる本文の列
  （Android の `CursorWindow`）は分割して読む。保留の表はコミット済みの状態なので、中断した処理は次の
  `indexMissing()` で再開する。`indexMissing()` は `ks_search_pending` に残っている行を飛ばすので、新しい記事は計算後の
  テキストで索引され、`''` で索引されることはない。すでに索引済みの記事は、日次の rebuild まで古いトークンのまま
  になる——フィード更新で本文が変わった場合と同じ、許容済みの古さである。
- **本文なしでマージされた記事。** 軽量行（既読・スター・削除の変更）は、その記事の本文を運ぶファイルより先に
  端末へ届くことがある——結果整合の一覧では後の差分が先に並びうる——ので、マージは `content` も `summary` もない
  記事を挿入する。すぐに索引すると `''` しか持たず、索引済みの行は二度と見直されないため、本文が届いた後も本文で
  検索できないままになる（単に古いのではない）。そこでマージはそのような記事を `ks_search_awaiting_body` に記録し
  （マージのトランザクションの中、articles の文の前に、id で照合）、`indexMissing()` はまだ本文のない間それを飛ばす。
  本文が付けば——後のマージ（どの本文の変更とも同じく `ks_search_pending` に登録する）からでも、この端末自身の
  フィード更新からでも——`indexMissing()` が記録を外し、ほかの新しい行と同じく索引する。差分の上では軽量行と
  本当に本文のないフィード項目を区別できないので、本文が届かないままの記事は次の日次 rebuild がタイトルで索引し、
  表を空にする。その rebuild より後に本文が届くと、その行はまた以前のトークンのまま残る——
  [known-issues.ja.md](known-issues.ja.md) の「差分同期: 行のテキストが変わっても検索トークンが差し替えられない」を参照。
- **healing 用の全再構築（`rebuildIndex()` = `'rebuild'`）**:
  `domain/StartupMaintenanceTasks.kt` の `maybeRebuildFtsIndex`（desktop と Android で共有）による日次アイドル
  pass（`local_settings.lastFtsRebuiltAt` の 24h ゲート + `ActivityCenter` アイドル。同期・フィード更新に加え、
  更新 → 同期の一連の処理（`refreshCycleRunning`。その更新と同期の間の一瞬も含む）も実行中でないこと）でのみ実行。増分投入以降に
  本文が更新されて古くなった既存行を作り直す。`'rebuild'` は各記事の現在の `search_text` を索引するので、
  `rebuildIndex()` はまず `indexMissing()` と同じく `ks_search_pending` の行を再計算する——そうしないと `''` のまま
  保留に残った記事がそのまま索引され、その後の `indexMissing()` は再計算はしても索引済みとして飛ばしてしまう。
  それでもなお保留に残った行（その間に本文が変わった行）は、`'rebuild'` と同じトランザクションの中で索引から外す
  （外部コンテンツの `'delete'`）。そこではその行の値は `'rebuild'` が索引した値とちょうど一致する。外した行は次の
  `indexMissing()` が再計算して索引する。`'rebuild'` はそれらの記事も索引したばかりなので、`ks_search_awaiting_body` も
  同じトランザクションの中で空にする。トランザクションは原子的で書き込みから始まり（読み手は再構築前後どちらかを
  見るだけ）、検索は `busy_timeout` で待つため、実行中の検索も 0 件にならない——ただし再構築が `busy_timeout` 以内に
  書き込みロックを手放す場合に限る。データベースは rollback journal モードで動くので、それより長く待った検索は
  `SQLITE_BUSY` で失敗し、`ArticleRepository.search` は結果なしを返す（文書化済みのベストエフォートの扱い。
  [error-design.ja.md](error-design.ja.md) を参照）。

2 つの索引ライタは**相互排他**とする: `FtsManager` は `indexMissing()` と `rebuildIndex()` を内部の
mutex で直列化する（このため両者は `suspend`）。日次 pass のアイドル判定は `ActivityCenter` のロックなしの
参照なので、その直後に始まったフィード更新は検知されず rebuild と重なり得る。重なりは常に無駄な作業
（rebuild は増分投入を包含する）であり、rebuild が `busy_timeout` を超えて書き込みロックを保持する規模では、
どの呼び出し元も catch しない生の `SQLiteException` になる。検索は**意図的に直列化しない**: 従来どおり
再構築が 1 つのアトミックなトランザクションであることと `busy_timeout` の待機に依存するが、これは再構築が
`busy_timeout` 以内に終わる場合にだけ成り立つ（上記を参照）。

desktop の起動時は `main.kt` の `runBlocking` から `FtsManager.ensureIndexed()`（初回作成 + 未索引行の増分
投入）を呼ぶ（索引不在のままウィンドウを開かせないため）。ライタ mutex はコルーチンベースで、この時点では
直前にディスパッチされた `.opml` インポートが短時間だけ保持し得るのみなので、メインスレッドで待っても
デッドロックしない。Android は代わりに、より軽い `ensureIndexedIfTableAbsent()` をプロセス起動のたびに
呼ぶ（理由は [db-schema.ja.md](db-schema.ja.md) の `articles_fts` 節「起動時」を参照）。Apple の SDK は
`KeryxSdk.start` でテーブルを作り（best effort）、欠けている行は `prepareSearchIndex()` が補完する。

## クラウド認証（OAuth PKCE + オフラインアクセス）

OAuth 2.0 authorization-code-with-PKCE のオーケストレーション（PKCE 生成・認可 URL 構築・その URL を開く・
state 検証・コード交換）はプロバイダー共通の `OAuthConnectFlow`（`commonMain`、Apple 版を含む全プラット
フォームで共有）に集約する。プロバイダー差は
**リダイレクトの受け取り方（`OAuthRedirectTransport`）とエンドポイント/スコープ（`CloudAuthManager` 実装）**
だけで、`DropboxAuthManager` / `GoogleDriveAuthManager` / `OneDriveAuthManager` が `CloudAuthManager` を実装する。いずれも
オフラインアクセス（Dropbox: `token_access_type=offline`、Google: `access_type=offline` + `prompt=consent`、OneDrive: `offline_access` スコープ）を
指定し**リフレッシュトークンを取得・保存**する。認可 URL を開く処理自体は、注入された
`domain/AuthorizationLauncher` を経由する（既定は `DefaultAuthorizationLauncher` で、システムのブラウザを開く）
——Apple 版が自前のものをどう渡すかは、後述の「Apple 版での OAuth 認可」を参照。

**唯一の例外が Android の Google Drive で、このフローをまったく通らない** —— `OAuthConnectFlow` も
`OAuthRedirectTransport` も使わず、リフレッシュトークンも持たない。Play 開発者サービスの
`AuthorizationClient` が同意のやり取りを丸ごと担い、短命なアクセストークンを直接発行して、必要に
なるたび再発行する。したがって本節の「トークン保存」までの記述は、デスクトップの 3 プロバイダーと
Android の Dropbox / OneDrive を指す。残る 1 件は後述の「Android での Google Drive」を参照。

リダイレクト受信方式はプロバイダーごとに選ぶ（設計方針 `.claude/rules/cloud-oauth-transport.md` 参照——両方使える場合はカスタム URI スキームを優先）:

- **Dropbox / OneDrive — カスタム URI スキーム**（`CustomUriRedirectTransport`）:
  - **仕組み。** リダイレクト URI は `keryx://oauth2/callback`。両プロバイダーで共有し `state` で識別
    する。desktop/Android では認可 URL を既定ブラウザーで開き、OS が URL を実行中インスタンスへ配送
    する（デスクトップの `LaunchArgDispatcher` が `parseOAuthUri` して共有 `MutableSharedFlow<OAuthCallbackParams>` に流す）。
    Apple 版は代わりに `ASWebAuthenticationSession` を使う——詳細は後述の「Apple 版での OAuth 認可」
    を参照。
  - **OneDrive 固有の事情。** Microsoft Identity platform（`consumers` テナント）と Microsoft Graph を
    使い、Google と違い**クライアントシークレット不要の PKCE パブリッククライアント**。同期 DB は
    アプリ専用フォルダー（`/me/drive/special/approot`、スコープ `Files.ReadWrite.AppFolder`）に保存する。
  - **OneDrive が個人アカウント限定である理由。** テナントセグメントは `common` ではなく `consumers`
    でなければならない。アプリ登録が「個人用 Microsoft アカウントのみ」（signInAudience = Consumer）
    であり、Microsoft はこの audience での `/common` を拒否する（"the application must not be
    configured with 'Consumer' as the user audience"）。しかもこの拒否はユーザーがメールアドレスを
    送信した*後*に返るため、汎用の認証失敗として現れる。登録を職場・学校アカウント対応に広げる選択
    も採れない。`Files.ReadWrite.AppFolder` は個人用アカウント限定の Graph 権限であり、組織アカウント
    に対応するにはユーザーのドライブ全体を対象とする `Files.ReadWrite(.All)` のような広いスコープが
    必要になって、`external-spec.md` のプライバシー方針に反するため。
  - **失効と排他制御。** Microsoft には標準のトークン失効エンドポイントが無いため
    `OneDriveAuthManager.revoke` は no-op で、連携解除はローカルトークンの破棄のみ。楽観的排他は
    DriveItem の `eTag` を `rev` として使い `If-Match` で送る（412→衝突）。`create` は
    `@microsoft.graph.conflictBehavior=fail`（409→衝突）。
- **Google Drive（デスクトップのみ）— ループバック**（`LoopbackRedirectTransport`）: Android はこのフローを一切使わない — 後述の「Android での Google Drive」を参照。Google の「デスクトップアプリ」クライアントは
  任意のカスタムスキームを許可せず、`http://127.0.0.1:<ポート>` のループバックのみを受け付ける。一時 HTTP
  サーバー（`com.sun.net.httpserver`。`jdk.httpserver` モジュール同梱済み）を立ててリダイレクトを受け、
  受信後に停止する。OS 側のスキーム登録は不要（`keryx://` の登録は Dropbox / OneDrive 用のまま）。**Dropbox とは異なり
  クライアントシークレット（`GOOGLE_DRIVE_CLIENT_SECRET`）もトークン交換・リフレッシュ両方に送る**——PKCE を
  使っていても、「デスクトップアプリ」タイプの Google OAuth クライアントは iOS/Android と違い完全な public
  client 扱いされず、省略すると Google のトークンエンドポイントが `invalid_request: client_secret is missing`
  で拒否する（詳細は [build.ja.md](build.ja.md)）。スコープは `drive.appdata` のみ（ユーザーの Drive 内のアプリ専用隠しフォルダ）。

OS へのスキーム登録方法はプラットフォームごとに異なる。Compose 版 macOS ビルド（内部検証専用）はパッケージング時に Info.plist
（`CFBundleURLTypes`）で宣言する。出荷版の SwiftUI アプリはスキームを登録しない（後述の「Apple 版での Google Drive」を参照）。Windows / Linux は起動時に `registerFileAssociations()` が登録し、
Windows は `HKEY_CURRENT_USER\Software\Classes\keryx`（ユーザー単位のハイブなので管理者権限は不要）を、Linux は `LinuxUriSchemeRegistrar` がユーザーレベルの
`.desktop`（`$XDG_DATA_HOME/applications/keryx-url-handler.desktop`、既定
`~/.local/share/applications/keryx-url-handler.desktop`）と `$XDG_CONFIG_HOME/mimeapps.list`
（既定 `~/.config/mimeapps.list`）の関連付けを書き出す。Linux の `.desktop` は `Exec` 行が `%u` で終わっている必要がある——これが無いと
Desktop Entry 仕様上 URI がプロセスに渡らず、ブラウザーはスキームを解決できずに「不明なプロトコル」
エラーを出す。いずれも OS が URL をコマンドライン引数としてアプリを起動し、`main.kt` が
single-instance 経由で実行中インスタンスへ転送する。

**Android** は同じ `keryx://oauth2/callback` スキームを宣言的に登録する:

- **登録。** `AndroidManifest.xml` の `MainActivity` に `intent-filter`（`VIEW`/`DEFAULT`/`BROWSABLE`、
  `scheme="keryx"` `host="oauth2"`）を持たせるだけで、Windows/Linux のような起動時登録処理は不要。
- **ディスパッチ。** `MainActivity.onCreate`/`onNewIntent` がリダイレクトのデータ URI を
  `dispatchOAuthCallbackIfPresent` に渡し、これがデスクトップの `main.kt` と同じ
  `classifyLaunchArg`（commonMain）/ `parseOAuthUri`（commonMain）で分類したうえで、同じ形の
  `MutableSharedFlow<OAuthCallbackParams>`（Android 自身の `platformModule` に登録された別インスタンス）
  へ流し込む。
- **構成変更。** `launchMode="singleTask"` により、既に起動中のインスタンスは新規 `onCreate` ではなく
  `onNewIntent` でリダイレクトを受け取る。ディスパッチ成功後は intent のデータをクリアしておく —
  そうしないと、後で回転などによる構成変更で `onCreate` が同じ `Intent` を再度受け取ったときに
  同じリダイレクトを二重処理してしまう。
- **スキームを排他専有できなくても安全な理由。** デスクトップと異なり、Android のカスタム URI
  スキームの `intent-filter` はアプリが排他的に専有できるものではない（別アプリが同じスキームを
  宣言しうる）ため、コード交換自体を実際に守っているのは（全プロバイダーで既に必須の）PKCE である
  ——横取りされても一致する `code_verifier` が無ければ意味を成さない。

> [!NOTE]
> **カスタム URI プロバイダーは全デスクトップ OS 共通**: `./gradlew :composeApp:run` では
> Dropbox / OneDrive 連携を完了できない。macOS（Compose 版ビルド、内部検証専用）では `keryx://` を LaunchServices がパッケージ版
> `Keryx.app` にルーティングするため、`gradlew run` のインスタンスにはリダイレクトが届かない。
> Windows / Linux では、起動時の登録がパッケージ版ランチャーからの起動でない限り意図的に何もしない
> （`packagedLauncherPath()`）——JDK の `java` バイナリを `keryx://` のハンドラーとして登録すると
> Gradle 実行終了後も残ってしまうため。連携を行う/確認する場合は `./gradlew :composeApp:createDistributable` でビルドした
> アプリを起動する（詳細は [setup.ja.md](setup.ja.md)）。
> Google Drive はループバック受信のため、この制約はなく `gradlew run` でも連携を完了できる。
> Android にはどちらの制約もない——`installGithubDebug` でもリリースパイプライン経由でも、マニフェスト宣言の
> `intent-filter` は同じように機能する。

### Android での Google Drive（Play 開発者サービスの `AuthorizationClient`）

Android の Google Drive は、本ドキュメントの他のどのプロバイダ・プラットフォームの組み合わせとも
異なる仕組みを使う — ブラウザリダイレクトではなく、Play 開発者サービスの `AuthorizationClient` である。
実装はすべて `:androidGms` の `data/cloud/PlayServicesGoogleDriveAuth.kt` にあり、このモジュールが
存在するのは `github` と `play` flavor だけ —— `fdroid` flavor は Play 開発者サービスを一切含まず、
Google Drive も提供しない。

- **デスクトップ向け構成を流用できない理由。** Google の OAuth ポリシーは Android クライアント種別に
  対して、カスタム URI スキーム（理由はアプリなりすましのリスク）とループバックリダイレクトの
  **両方**を廃止している。リダイレクトを使うフローが残っていないため、デスクトップの
  「デスクトップアプリ」クライアント（ループバック + `client_secret`）に Android での等価物は無い。
  これは Google 固有のポリシー判断であって Android 一般の制約ではない — Dropbox と OneDrive の
  カスタム URI リダイレクトは Android でも同じように動作する。
- **`AuthorizationClient` が代わりに提供するもの。** `drive.appdata` スコープでの `authorize()` は、
  短命（1 時間）のアクセストークンを端末上で直接返す。初回のみ `PendingIntent` 経由で同意画面が出て、
  以降は付与が有効なかぎり**ユーザー操作なしで**応答する。付与を所有するのは Play 開発者サービスなので、
  **リフレッシュトークンも `client_secret` もバックエンドサーバも不要**。バックエンドが要るのは
  オフライン版（`AuthorizationResult.getServerAuthCode()`）だけで、こちらは意図的に使っていない。
- **ビルドにクライアント ID を持たない。** Android OAuth クライアントはパッケージ名 + 署名証明書の
  SHA-1 で照合される（Cloud Console への登録手順は [build.ja.md](build.ja.md) 参照）ため、
  `BuildConfig` から読む値は無い。したがって未登録の署名鍵でビルドした場合、ビルド時ではなく
  `authorize()` の失敗として現れる。確認すべきクライアント ID が無いので、`PlayServicesGoogleDriveBackend`
  は `CloudSession.Provider.isConfigured` を `true` とする — Google Drive を選択肢に出すかどうかは、次の
  端末での判定が決める。
- **配信チャネルではなく端末で判定する。** `CloudStorageAvailability.googleDriveAvailable` は
  登録済みの `AndroidGoogleDriveBackend` に問い合わせる（`:androidGms` の実装は
  `GoogleApiAvailability.isGooglePlayServicesAvailable(...) == SUCCESS` を返す）。これをプロセスごとに
  一度だけ評価し、`platformModule` はそれが真のときだけプロバイダを登録する。バックエンドが何も
  登録されていない場合（`fdroid` flavor）の答えは単に「利用不可」。脱 Google の ROM（GrapheneOS、
  GApps なしの LineageOS）では Google Drive が選択肢に出ないだけで、Dropbox・OneDrive・ローカルのみは
  影響を受けない。`github`/`play` のプロダクトフレーバーでは**意図的に**分岐しない — play フレーバーの
  APK もサイドロードされうるし、github フレーバーの APK も Play 開発者サービスのある端末で問題なく動く。
  `AndroidUpdateInstaller` が `REQUEST_INSTALL_PACKAGES` に適用しているのと同じ考え方。
- **`CloudSession` 内でのトークンのライフサイクル。** リフレッシュトークンが無いため、通常の
  保存トークン経路（`CloudSession.CredentialLifecycle.OAuth`）では「期限切れでリフレッシュトークンが
  無い」分岐に落ち、すでに失効したトークンを返してしまう。このプロバイダのライフサイクル
  `CloudSession.CredentialLifecycle.PlatformOwned` は、まさにこのケースのためにトークン供給を置き換える: クラウドリクエストのたびに Play 開発者サービスへ問い合わせる
  （`allowUserInteraction = false`。リクエスト、まして `WorkManager` のバックグラウンド同期が
  独断で同意画面を開いてはならないため）。接続時のトークンは従来どおり `KeystoreTokenStorage` に
  書くが、これは再起動後も `connectedType()` が「接続済み」と報告できるようにするためだけであり、
  `expiresAtMillis` は `null` — Play 開発者サービスは有効期限を返さず、推測値を入れるのは
  「不明」と認めるより悪いからである。
- **再同意。** ユーザーが Google アカウント側で付与を取り消すと、同期は `CloudAuthException` で
  失敗するようになり、既存の同期エラー経路が `ShowSettingsTab("cloud_sync")` 付きで通知センターに
  記録する — Dropbox のリフレッシュトークンが失効したときとまったく同じ扱いである。
  ここからの回復は「連携」を押し直すだけでは済まない。付与が取り消されても保存済みトークンは
  そのまま残るため `connectedType()` は接続済みと報告し続け、そもそも行に「連携」ボタンが出ないからである。
  直すのは切断 — Play 開発者サービスのキャッシュを落とすのはこちらの処理（後述の **切断** を参照）—
  とそれに続く接続である。`CloudSyncTab` はこれを 1 つの操作として提供する:
  `SyncRepository.lastSyncAuthFailed` が立っている間、接続済み行の 1 番目のアクションが
  *同期データをリセット* に代わって **連携し直す**（`SettingsViewModel.reconnect`。解除してから
  同じプロバイダへ接続し直す）になる。並べるのではなく差し替えるのは、ボタンを 1 つ増やすと
  状態によって行の子要素数が変わり、デスクトップのラベル付きボタンがプロバイダ名と分け合う幅も
  超えてしまうためであり、そもそもこの 2 つは排他的でもある: リセットには自前の有効な認可が必要で、
  認可こそが壊れている状況で提示すべき回復手段ではない。*連携を解除* はどちらの場合も隣に残るので、
  やめるために先に直す必要は無い。

  `PlayServicesConnectFlow` が認可要求の前にキャッシュを落とすのも同じ理由による。こちらが
  カバーするのは、**接続済みではないのに** Play 開発者サービスのキャッシュだけが付与より長生き
  している場合 — 以前の切断で `clearToken` が失敗していた、再インストールした、
  アプリのデータを消したがキャッシュは残っていた、といったケースである。これが無いと、
  その状態での接続が死んだトークンで黙って成功してしまう。コストは明示的なユーザー操作 1 回につき
  Play 開発者サービスへの往復が 1 回増えるだけで、付与が健全なら新しいトークンが黙って発行され、
  同意画面は出ない。
- **切断。** `PlayServicesGoogleDriveAuthManager.revoke` は保存済みのアクセストークンを無視し
  （その時点では 1 時間以上経っており、Google の revoke エンドポイントに拒否される）、
  ユーザー操作なしで新しいものを取得して、デスクトップと同じ `GOOGLE_REVOKE_ENDPOINT` へ POST する。
  それも取得できない場合は、切断の途中で同意画面を開くのではなく成功として報告する。いずれにせよ
  `CloudSession.disconnect` はローカルのトークンを削除する。
  **その後、同じトークンに対して `AuthorizationClient.clearToken` を呼ぶ。これは後片付けではなく必須の手順である。**
  上記の取り消しは Play 開発者サービスの外側の素の HTTPS 通信なので、Play 開発者サービスは自分が
  キャッシュしている認可が死んだことを知らない。そのまま `authorize()` にキャッシュから成功を返し続け、
  `hasResolution()` も立てない。結果、再接続は同意画面なしで完了し、以後すべての Drive リクエストが
  401 で失敗して、アプリ側に回復手段が無くなる。
  なお `AuthorizationClient.revokeAccess` は HTTPS の取り消しを丸ごと置き換えられそうに見えるが、
  このフローが別途持っていない `Account` を必須とし、指定しないと Play 開発者サービス内部で
  `NullPointerException: ... Account.name on a null object reference` になる。
- **同意画面には Activity が必要。** `AuthorizationClient` が返す `PendingIntent` は Activity からしか
  結果付きで起動できないため、`platform/AndroidAuthorizationHost.kt` が `MainActivity` の
  `StartIntentSenderForResult` ランチャーを接続フローへ橋渡しする — `AndroidFilePickerHost` と
  同じ形で、同じ理由による。Activity が接続されていない場合は `null` に解決され、これが
  バックグラウンドでの正しい結果となる。

`appDataFolder` は **OAuth クライアント単位ではなく Cloud プロジェクト単位**でスコープされるため、
既存のデスクトップ用クライアントに Android クライアントを追加しても、両方の端末が同じ隠しフォルダを
読み書きする。確かめ直すには、同一プロジェクト内の別の OAuth クライアントから `appDataFolder` を一覧する。
もう一方のクライアントが作ったファイルが見えるはずである。この性質が無ければ、デスクトップと Android は
別々のファイルへ黙って同期してしまう。

### Apple 版での Google Drive（secret 不要な「iOS」タイプの OAuth クライアント）

Apple 版（`:shared` の appleMain。macOS と iOS が対象）は、Android のように Play 開発者
サービスや端末側の認可 API を必要とせず、通常の `OAuthConnectFlow` + `CustomUriRedirectTransport`
の経路をそのまま使う — ただし desktop 版とは別のクライアントを使う。

- **desktop 版のクライアントを再利用できない理由。** desktop 版の「デスクトップ アプリ」クライアントは
  loopback リダイレクトと `client_secret` を前提とする（上記「Google Drive（デスクトップのみ）— ループバック」
  を参照）。secret をネイティブアプリのバイナリに同梱すると、バイナリ自体から抽出されてしまう。Google
  がネイティブ Apple アプリ向けに用意している答えが **「iOS」アプリケーションタイプ**で、secret を一切
  要求しない（「iOS」タイプは iOS/iPadOS 専用ではなく、ネイティブ macOS アプリにも使われる — 詳細は
  [build.ja.md](build.ja.md) を参照）。Google のトークンエンドポイントは、この種類のクライアントに対しては
  `client_secret` なしのトークン交換・リフレッシュを受け入れる。これは「デスクトップ アプリ」クライアント
  （PKCE でも `invalid_request: client_secret is missing` で拒否される。上記参照）とは異なる。
  `GoogleDriveAuthManager.clientSecret` を nullable にしたのはこのためで、desktop 版は secret を渡し、
  Apple 版は `null` を渡してリクエストからパラメーター自体を省く。
- **リダイレクト URI。** 「iOS」タイプのクライアントが受け付けるリダイレクトは、Dropbox・OneDrive が使う
  共通の `keryx://oauth2/callback` ではなく、クライアント ID を逆順にした自分専用のカスタム URL スキーム
  だけ：`NNNN-xxxx.apps.googleusercontent.com` → `com.googleusercontent.apps.NNNN-xxxx:/oauth2redirect`。
  `googleIosClientRedirectUri(clientId)`（`data/cloud/GoogleDriveAuthManager.kt`）がこれを導出する純粋
  関数で、`ApplePlatformModule.kt` の `appleGoogleDriveProvider` がその結果を `CustomUriRedirectTransport`
  の `redirectUri` に渡す。`cloudSessionSingles` が Dropbox・OneDrive 用に用意する既存の
  `MutableSharedFlow<OAuthCallbackParams>` をそのまま共用し、どちらのスキームでリダイレクトが届いても
  `state` で判別する。Swift 側アプリは、このスキームも `keryx://` も Info.plist に登録しない——OS が
  カスタムスキームのリダイレクトをルーティングする代わりに `ASWebAuthenticationSession` を開くので、
  必要なのはそのセッション自身の `callbackURLScheme` だけ——詳細は後述の「Apple 版での OAuth 認可」
  を参照。
- **別クライアントだが同じ Cloud プロジェクト。** Apple 用クライアントは、上記の Android の場合と同様に
  desktop 版とは別の OAuth クライアントだが、パッケージ署名で自動照合されるのではなく Cloud Console で
  手動作成する — Google の「iOS」クライアントタイプには Android の SHA-1 照合に相当する仕組みが無いため、
  クライアント ID はビルド時定数から読む（`AppleBuildConfig.GOOGLE_DRIVE_CLIENT_ID`。`DesktopBuildConfig`
  と同じ方式で `appleMain` にだけ生成される — 詳細は [build.ja.md](build.ja.md)）。上記と同じ理由で、
  desktop・Android のクライアントと同じ Cloud プロジェクトに置く必要がある。別プロジェクトにすると、
  Apple 版だけ他の端末と異なる隠しフォルダを読み書きしてしまう。
- **有効化の判定。** `CloudStorageAvailability.apple.kt` の `googleDriveAvailable` は
  `AppleBuildConfig.GOOGLE_DRIVE_CLIENT_ID.isNotEmpty()` — 他のプロバイダー／プラットフォームの組と同じ
  「ID が空なら選択肢を隠す」という規約に従うので、Apple 用クライアントを設定していないビルドでは
  Google Drive が単純に表示されない（未設定の Dropbox キーで Dropbox が隠れるのと同じ）。
- **トークンとリフレッシュ。** Android の Play 開発者サービス経路とは異なり、Apple 版は本物のリフレッシュ
  トークンを持ち、Dropbox・OneDrive と同じく `KeychainTokenStorage` に保存する — ライフサイクルは通常の
  `CloudSession.CredentialLifecycle.OAuth` であり、Play 開発者サービス風の `PlatformOwned` ではない。

### Apple 版での OAuth 認可（`ASWebAuthenticationSession`）

Apple 版のどのプロバイダーも、`OAuthConnectFlow` + `OAuthRedirectTransport` の組み合わせ自体は desktop と
同じ（Dropbox・OneDrive は `keryx://`、Google Drive は自分専用のクライアント ID 逆順スキーム、いずれも
カスタム URI スキーム）。違うのは**認可 URL をどう開き、リダイレクトをどう受け取るか**——Apple 版はカスタム
URI スキームを OS に登録せず、ブラウザも自分では開かない：

- `OAuthConnectFlow` は認可 URL を、`platform/BrowserOpener` を直接呼ぶのではなく、注入された
  `domain/AuthorizationLauncher`（`fun interface { fun launch(authorizeUrl: String, redirectUri: String) }`）
  経由で開く。`domain/DefaultAuthorizationLauncher`——どのプラットフォームでも既定——はシステムのブラウザ
  で開く。
- `KeryxSdk.start` の `openAuthorization: ((url: String, callbackScheme: String) -> Unit)?` 引数で、
  Swift 側が自前のランチャーを渡せる。渡された場合、`KeryxSdk` はこれを `AuthorizationLauncher` として
  ラップし、接続フロー自身の `redirectUri` から `domain/schemeOf`（先頭の `:` より前をすべて取る）で
  `callbackScheme` を導出してからクロージャーに両方を渡す。Swift 側アプリは
  `ASWebAuthenticationSession(url:callbackURLScheme:)` を開く——OS がスキームをルーティングするのではなく
  セッションが直接コールバックを受け取るので、どのプロバイダーについても Info.plist の
  `CFBundleURLTypes` 登録は不要。
- セッションの完了ハンドラーは、そのコールバック URL を `KeryxSdk.handleOAuthRedirect(url)` に渡す——
  desktop/Android で OS がルーティングする `keryx://` リダイレクトとまったく同じ扱いで、両者とも同じ
  `MutableSharedFlow<OAuthCallbackParams>` を `state` で識別して流れるだけなので、`OAuthConnectFlow`
  自身はどちらが届いたのか区別できない。
- ユーザーがセッションをキャンセルした場合は、Swift 側が接続フロー自身のコルーチン（`Task`）をキャンセル
  する。`OAuthConnectFlow` 自体には別途呼び出すキャンセル経路は無い。

### Nextcloud（Login Flow v2）

Nextcloud には OAuth を使わず、アプリ専用フォルダーもない。関連する実装はすべて `data/cloud/nextcloud/` にある。

- **サーバー。** 利用者はダイアログでサーバーのアドレスを入力する（`presentation/settings/NextcloudServerController`。
  両 UI と、すべての接続経路——セットアップ・接続・切り替え・再接続——が共有する）。`normalizeNextcloudUrl` は、
  スキームのないアドレスに `https://` を付け、それ以外のスキーム（`http://` を含む）や、認証情報・クエリ・フラグメントを
  含むアドレスを拒否し、ブラウザから貼り付けた URL をサーバーのベース（`…/index.php/…`、`/login`、末尾のスラッシュを
  除いたもの）まで切り詰める。続いて `NextcloudServerProbe` が、`GET {base}/status.php` が 200 と `installed: true` を
  返すことを、リダイレクトを追わずに確かめる（3xx は「Nextcloud が見つからない」として扱う）。失敗にはそれぞれ専用の
  `ErrorKind`（HTTPS が必要 / 見つからない / 到達できない）があり、`NextcloudServerException` が運ぶ。証明書は OS が
  信頼するものだけを受け付ける。再接続では、保存済みのサーバー（`CloudSyncController.reconnectServerUrl`。再接続が
  認証情報を消す前に読む）をダイアログの初期値にする。他のプロバイダーに接続中に Nextcloud を選んだ場合は、切り替えの
  確認が済んでからサーバーを尋ね、ダイアログをキャンセルすれば今の接続はそのまま残る。
- **サインイン（`NextcloudLoginFlow`）。** `POST {base}/index.php/login/v2` がサインインページとポーリング用の
  トークン・エンドポイントを返す。ページは `domain/LoginPageLauncher` で開く——デスクトップと Android ではシステムの
  ブラウザ（`BrowserLoginPageLauncher`）、Apple ではコールバックスキームなしの `ASWebAuthenticationSession`
  （`KeryxSdk.start` の `openLoginPage` / `closeLoginPage`）。その後フローは、毎秒（`NEXTCLOUD_LOGIN_POLL_INTERVAL_MS`）
  トークンをポーリング用エンドポイントに POST する。利用者がアクセスを許可するまでは 404、許可すると一度だけ 200 で
  `server`・`loginName`・`appPassword` が返る。サーバーは 20 分（`NEXTCLOUD_LOGIN_TIMEOUT_MS`）でこの要求を忘れる。
  途中のポーリングの失敗は単に再試行する。`loginName` は WebDAV のパスに必要なユーザー ID と一致するとは限らないので、
  ID は OCS の `GET /ocs/v1.php/cloud/user`（`ocs.data.id`）から読む。ベース、サインインページ、ポーリング用
  エンドポイント、許可された `server` はすべて HTTPS でなければならない。フローが最後まで進めなかった（ユーザー ID が
  読めなかった）アプリパスワードは失効させる。フローがどう終わっても、ページを開いたあとは `LoginPageLauncher.close()`
  を呼ぶ：Apple はセッションを取り消し、デスクトップはウィンドウを前面に戻し（ブラウザのタブは外から閉じられない）、
  Android は自身の起動 intent を `CLEAR_TOP` 付きで開始して、`singleTask` のタスクを Custom Tab の上に戻す。
  サインインを待っている間は、最長 20 分かかりうるため、両 UI ともブラウザでのサインインを待っていることを表示する。
  User-Agent はデバイスをサーバーに名乗るもの（`Keryx (Android)` など）で、アカウントの「デバイスとセッション」に
  アプリパスワードの名前として出る。
- **ストレージ（`NextcloudStorage`）。** 同期ファイルは利用者自身のファイルの `/Keryx/` に置く
  （`{server}/remote.php/dav/files/{userId}/Keryx/keryx-sync.json` など）。すべてのリクエストにアプリパスワードを HTTP
  Basic の認証情報として付け、保存済みのサーバー URL が HTTPS でなければ送らない。リダイレクトは追わない。
  `metadata` は `getetag` を求める Depth 0 の `PROPFIND`（名前空間の接頭辞に関係なくローカル名で照合する。404 →
  存在しない）、`download` は `ETag` をリビジョンとする `GET`、`upload` は期待するリビジョンをそのまま `If-Match` に
  入れた `PUT`、`list` は `getetag` と `getcontentlength` を求める Depth 1 の `PROPFIND`。一覧ではマルチステータス中の
  リソースごとのステータスを読む: `/Keryx` 自体、または接頭辞に一致するファイルの失敗ステータスはストレージエラー
  とし（空の一覧にはしない）、それ以外のメンバーの失敗ステータスは無視する（ユーザー自身のファイルであるため）。
  プロパティは成功した `propstat` からのみ読む。
- **リビジョン。** リビジョンはファイルの ETag で、Nextcloud は引用符も含めて完全一致で比較する。`If-Match` が一致
  しない（またはファイルがない）と 412（期待するリビジョンがなければ `If-Match` を送らず無条件に `PUT` する）、ファイルのロックを持つ同時上書きがあると 423 になり、どちらも
  `SyncConflictException`。書き込んだリビジョンは書き込み自身の応答の `OC-ETag` / `ETag` ヘッダーから読み
  （`CloudStorage.kt` の `headerRevOrConflictOr`）、後続のリクエストからは決して読まない。
- **上書きしない作成。** Nextcloud は `If-None-Match: *` をアトミックに適用しないので、初回アップロードの保護に使えない。
  代わりに `create` は `/Keryx` があることを確かめ（`MKCOL`。405 はすでにあるという意味）、一時名
  `/Keryx/.upload-<uuid>.tmp` にアップロードしてから、`Overwrite: F` 付きの `MOVE` で本来の名前に移す——移動先が
  すでにあれば上書きせず 412（競合）、別の書き込みが移動先をロックしていれば 423（同じく競合）になり、2 台がともに自分がファイルを作っていると思い込める隙間が、アップロード
  全体から移動の瞬間だけに縮む。`MKCOL` や一時ファイルへのアップロードが 423（別の書き込みが `/Keryx` かそのパスを
  ロックしている）を返した場合も競合とし、ストレージエラーとして報告せず同期のリトライに任せる。
  移動が行われなかった場合は一時ファイルを削除する。その削除にも失敗したものは
  `/Keryx` に残る。その名前は同期ファイルのパターンに合わないので、一覧取得では無視される。あとで片付けることは
  しないが、これは受容している。
- **リネーム。** `Overwrite: F` と完全な URL の `Destination` を付けた `MOVE`。移動元がない（404）場合は完了とみなし、
  移動先が埋まっている（412）場合はストレージエラーにする。
- **失効。** アプリパスワードには期限がないので、ライフサイクルは `Static`。連携の解除では
  `DELETE /ocs/v2.php/core/apppassword`（`OCS-APIREQUEST: true` 付き）を呼び、その成否にかかわらずローカルの認証情報を
  消す。
- **権限範囲。** アプリパスワードは `/Keryx` だけでなくアカウント全体にアクセスできる——Nextcloud には他のプロバイダー
  のようなアプリフォルダーのスコープがない。接続ダイアログと `PRIVACY.md` でそのことと、取り消し方、Nextcloud 36 以降で
  ファイルへのアクセスだけに制限する方法を示す。
- **サーバー上の副作用。** アップロードのたびに版（files_versions アプリ）とアクティビティの記録が増える。利用者の
  ファイルを同期しているデスクトップ版 Nextcloud クライアントは、そちらで除外しない限り `/Keryx` もダウンロードする。
  利用者向けの案内は `PRIVACY.md` と README にある。
- **Apple でのローカルネットワーク。** ローカルネットワーク上のサーバーに接続すると、iOS（と macOS 15）がローカル
  ネットワーク利用の許可ダイアログを出す。その説明文は `NSLocalNetworkUsageDescription` で、`InfoPlist.xcstrings` で
  ローカライズする（[build.ja.md](build.ja.md) の「Apple アプリ用の String Catalog」を参照）。

### トークン保存先

**プロバイダーごとに別インスタンス**の `TokenStorage` を DI（`platformModule`）で構築する（1 インスタンスを
複数プロバイダーで共有しない。`SecurityCliTokenStorage`/`KeystoreTokenStorage` は結果をインスタンスに
キャッシュするため共有すると壊れる）。
Keychain のアカウント名とフォールバックファイル名は `CloudStorageType.id` から導出する（Dropbox は `"dropbox"` で
従来のハードコード値と一致するため既存トークンの移行は不要。Google Drive は `"google_drive"`、OneDrive は `"onedrive"`、Nextcloud は `"nextcloud"`）。

**保存形式。** どの保存先も、プロバイダーの `CloudCredentials`（`data/cloud/CloudCredentials.kt`）を
`CloudCredentialsSerializer` で JSON にして保存する。このシリアライザはキーで種類を判定し（`appPassword` キーが
あれば `AppPasswordCredentials`、なければ `OAuthTokens`）、クラスの discriminator を書かない。そのため `OAuthTokens`
は `CloudCredentials` 導入前とまったく同じ形で保存され、古いビルドが保存したトークンもそのまま読める。sealed
クラスの既定のシリアライザに切り替えてはならない。既定のものは `"type"` キーを必須とするため、保存済みのトークンが
すべてデコードできなくなり、利用者は気付かないうちにプロバイダーが未接続になってしまう。

**認証情報のライフサイクル。** 各 `CloudSession.Provider` は、保存した認証情報をどう有効に保ち、どう失効させるかを
`CloudSession.CredentialLifecycle` で示す。`OAuth`（Dropbox、OneDrive、デスクトップと Apple の Google Drive）は、
期限切れのアクセストークンを保存済みのリフレッシュトークンで更新して保存し直し、切断時にアクセストークンを失効させる。
`PlatformOwned`（Android の Google Drive）は、リクエストのたびにプラットフォームから新しいアクセストークンをもらい、
リフレッシュも保存も行わず、切断時に保存済みのアクセストークンを失効させる（「Android での Google Drive」参照）。
`Static`（Nextcloud）は、期限のない認証情報（アプリパスワード）を保存したまま渡し、切断時にプロバイダー自身の失効処理を呼ぶ
——Nextcloud ではサーバー上のアプリパスワードを削除する。「Nextcloud（Login Flow v2）」参照。

`KEYCHAIN_SERVICE`（`works.merc.keryx`、`data/cloud/KeychainCoordinates.kt`）はデスクトップの全 OS で共通。

- Windows/Linux: OS セキュアストレージ（java-keyring — Credential Manager / Secret Service,
  `KeyringTokenStorage`）。
- macOS（Compose 版ビルド、内部検証専用）: Apple 署名の `/usr/bin/security` CLI に委譲（`SecurityCliTokenStorage`）。java-keyring は共有 JVM
  から Keychain 書き込みに失敗するため、Compose 版 macOS ビルドのみ `security` 経由にしている。項目は通常のログイン
  Keychain に入る——下のネイティブ Apple アプリはサービス名こそ同じだが、入れ物が別。
- ネイティブ Apple アプリ（macOS/iOS、`:shared` の appleMain）：`KeychainTokenStorage` が Security フレームワーク経由で
  Keychain に直接書き込む——サービスは `works.merc.keryx`、アカウントはどのプロバイダーも同じ。ただし
  `security` が読み書きする通常のログイン Keychain ではなく、**Data Protection Keychain**
  （`kSecUseDataProtectionKeychain`。出荷版アプリの `keychain-access-groups` エンタイトルメントが前提）
  に保存するので、サービス名・アカウントが同じでも Compose 版がそもそも到達できない別の入れ物になる。
  この分離は `KeryxSdk.start` の `useDataProtectionKeychain = true` だけに依存しており、テスト向けの
  既定値 `false` のままだと Compose 版のログイン Keychain 上の項目を共有してしまう。平文への
  フォールバックはない（書き込みの失敗は `NOT_PERSISTED`）。Compose 版が保存した項目からの移行は行わない：
  ネイティブアプリは常に再接続から始まり、同期済みのデータはクラウドから戻る。Google Drive は、
  `AppleBuildConfig.GOOGLE_DRIVE_CLIENT_ID` が設定されていれば提供し、空なら選択肢を隠す。前述の「Apple 版での
  Google Drive（secret 不要な「iOS」タイプの OAuth クライアント）」を参照。
- Linux のうち Snap パッケージ内だけは、`KeyringTokenStorage` の代わりに `LibSecretTokenStorage` を使う
  （`platform.isSnap` で分岐）。JNA 経由で libsecret を直接呼び出す実装で、libsecret がサンドボックスを
  検知して生の Secret Service ではなく Secret portal（`org.freedesktop.portal.Secret`）経由にルーティング
  し、その portal から得たアプリ専用のマスターシークレットでトークン JSON をローカルファイルに暗号化
  して保存する。スナップは `password-manager-service` プラグを一切宣言していない（Snapcraft の
  レビュアーはこのインターフェースの auto-connect を原則却下するうえ、手動で接続したところで
  使い道もない——`KeyringTokenStorage` はスナップ内からは意図的に到達不能）。詳しい理由は
  `build.ja.md` の「Linux Snap パッケージ」参照。スナップ外では適用しないため、既存の
  deb/rpm 利用者の Secret Service アイテムには影響しない。
- **フォールバックファイルと結果報告**:
  - 上記いずれも失敗時はデータディレクトリの `.{CloudStorageType.id}_tokens.json`（0600。Dropbox は
    `.dropbox_tokens.json`）へフォールバック。DI が `isMacOs`／`isSnap` で3つを切り替える
    （`PlatformModule.desktop.kt` の `providerTokenStorage`）。
  - `TokenStorage.save()` はトークンが実際にどこに残ったかを返す（`TokenSaveOutcome.SECURE` =
    セキュアストア / Android の Keystore 暗号化ファイル、`PLAINTEXT_FILE` = 平文フォールバック
    ファイルから読める（セキュアストアに到達できなかった場合と、セキュアな書き込みは成功したが
    古いフォールバックのコピーを削除できなかった場合の両方を含む）、`NOT_PERSISTED` = どちらにも
    書けず、アプリ終了までしか残らないため再起動後に再接続が必要）。
  - **保存できなかったトークンはメモリに保持する。** `NOT_PERSISTED` のとき、`CloudSession`（プロセス
    全体で1つのシングルトン）はそのプロバイダのトークンをメモリに保持し、ストアより優先して読む
    （接続済みかどうかの判定、アクセストークンの供給とそのリフレッシュ、切断時の revoke のすべて）。
    これによりアプリ終了までは同期を続けられる。これがないと、接続は成功と表示されるのに、同期は
    すべて「未接続」としてスキップされてしまう。その後ストアへの保存に成功した場合や切断した場合は、
    メモリ上のコピーを破棄する。
  - **トークンの書き込みは切断と直列化する。** `CloudSession` は、リフレッシュとその保存、接続直後の
    保存、切断時の revoke と削除を1つの mutex の下で実行する。これがないと、リフレッシュがネットワークを
    待っている間に切断が走ってストアを消しても、その後リフレッシュが新しい（revoke されていない）
    トークンを書き戻してしまう（ディスク上でも、上記のメモリ上のコピーでも）。ロックが掛かるのはこの
    トークン処理だけで、返したトークンを使うクラウドリクエスト自体には掛からない。
  - 劣化した2つの結果については、`CloudSession` がそれぞれ別のメッセージで、集約（coalescing）した
    `WARNING` 通知（原因と対処法を示す `ShowInfoDialog` アクション付き）を発行する。初回接続時も
    バックグラウンドのトークンリフレッシュ時も同様。フォールバック自体は引き続き許容する
    （`SECURITY.md` に記載のとおり、意図的な graceful degradation）が、黙って行われてはならず、
    また何も保存できなかった場合を「平文ファイルに保存した」と報告してはならない、という位置づけ。
  - **clear-on-success。** セキュアな書き込みが成功した際、デスクトップのセキュアストア実装はいずれも
    以前の劣化した保存で残った古いフォールバックファイルを削除し、セキュアストレージが再び使える
    ようになった後も平文コピーがディスクに残り続けないようにする — Android の `KeystoreTokenStorage`
    （後述）と同じ clear-on-success の挙動である。`KeyringTokenStorage`/`LibSecretTokenStorage` は
    この合成ロジックを共通の `SecretStoreTokenStorage` から継承し、`SecurityCliTokenStorage` も
    そのバックエンド `SecurityKeychainStore` が継承したうえで、メモリ内キャッシュを重ねるだけである。削除の確認が取れなかったフォールバッククリアは、
    `SECURE` と偽って報告するのではなく `PLAINTEXT_FILE` へと結果を降格する。
- Compose 版 macOS ビルド（内部検証専用）は書き込み後に **read-back 検証**（login keychain を明示指定して読み戻し）を行い、永続化を確認できない
  場合は file フォールバックへ回す。**書き込みの永続性は起動セッション依存**: パッケージ版（GUI ログイン
  セッション）では login keychain に永続化されるが、`gradlew run`（launchd 直下の Gradle daemon 配下の
  切り離しセッション）では `security add` が成功を返しても永続化しないため file に保存される。**読み取りは
  どちらのセッションからでも可能**（一度パッケージ版で連携すれば以降 `gradlew run` でも接続を引き継げる）。
- **Android**:
  - **Google Drive は本節のすべての例外。** そのトークンを所有するのは本アプリではなく Play 開発者
    サービスである（前述の「Android での Google Drive」参照）。リフレッシュトークンは一切保存されず、
    ここに書かれるアクセストークンも、再起動後に「接続済み」と報告するためだけに存在する —
    実際のリクエストに使うトークンは都度 Play 開発者サービスから取得する。仕組み（同じ
    `KeystoreTokenStorage`、同じフォールバックと結果報告）は以下と同一だが、守っている秘密は
    はるかに軽い — 長命なリフレッシュトークンではなく 1 時間のアクセストークンである。
  - **暗号化。** `KeystoreTokenStorage` が Android Keystore 保持の AES-256/GCM 鍵（プロバイダーごとに
    `CloudStorageType.id` 由来の別エイリアス。鍵の実体は端末が対応していれば Keystore/TEE から一切
    出ない）でトークン JSON を暗号化し、`IV || 暗号文` を `Context.filesDir` 配下の
    `.{CloudStorageType.id}_tokens.enc` に書く。鍵は `setUserAuthenticationRequired(false)` で
    生成する — 定期実行される `WorkManager` のバックグラウンド同期は端末ロック中でもトークンを
    復号できる必要があり、通常のトランザクションごとの秘密情報とは異なる要件のため。
  - **復号失敗とフォールバック。** 復号失敗（Keystore のリセット、ハードウェア鍵を引き継げない
    端末/OS 移行など）はクラッシュとしてではなく「トークン未保存」と全く同様に扱い、復号不能な
    ファイルは残さず削除する。Keystore 自体が使えない端末は、デスクトップが最終手段として使うのと
    同じ平文の `FileTokenStorage` にフォールバックする。
  - **clear-on-success。** 暗号化保存が成功した場合はこのフォールバックファイルを `clear()` し、
    `SECURE` / `PLAINTEXT_FILE` の判断はその `clear()` 自身の報告から決める——`TokenStorage.clear()`
    は `TokenClearOutcome.CLEARED` / `DATA_MAY_REMAIN` を返し、`FileTokenStorage` は削除試行後に
    ファイルがまだディスク上にあるか（`File.delete()` が false を返した場合は残る）で判定する。
    消し切れずに残った平文のコピーは `SECURE` ではなく `PLAINTEXT_FILE` として報告し、気付かれない
    ままディスク上に読める状態で残るのではなく警告の対象にする。
  - **判定がファイルの存在であって `fallback.load()` ではない理由。**
    `FileTokenStorage.load()` は JSON がデコードできなくなったファイルを「未保存」として報告する
    一方、その中の refresh token はそのまま読める状態で残るため、`load()` から消去を推測すると、
    まさに最も警告が必要なケースで `SECURE` を返してしまっていた。
  - **バックアップからの除外。** `.enc` ファイルと平文フォールバックの `.json` ファイルはどちらも
    Android の自動バックアップ/デバイス間転送から除外している（`AndroidManifest.xml` の
    `dataExtractionRules`/`fullBackupContent`）——長寿命の OAuth リフレッシュトークン（や、アカウント全体に
    アクセスできる Nextcloud のアプリパスワード）をバックアップに乗せるべきではなく、また Keystore 暗号化されたファイルはそもそも別端末に復元しても役に立たない
    ため。

### 今後の課題（未対応）

- **file → Keychain 移行 heal**: `.dropbox_tokens.json` にトークンがあり Keychain が空の場合、
  `SecurityCliTokenStorage.load()` で file の値を Keychain へ書き戻し、**read-back 検証に成功した時のみ**
  file を削除する予定（検証失敗時は file を保持しデータ損失を防ぐ）。未実装 — 現在の `load()` は file への
  フォールバックのみで、Keychain への書き戻しは行わない。

## 同期対象の記事範囲

起動時のキャッシュ削除は、保持期間を過ぎた記事を物理削除せず**論理削除**（`deleted_at` / `deleted_updated_at` を
打刻）する。トゥームストーンは軽い行として運ばれ、マージ（保持グループの後勝ち）で伝わるので、削除を
見逃した端末も、記事を再追加するのではなく収束する。トゥームストーンの物理的な回収はまだ行わない（今後の課題）。

キャッシュ削除は `cached_at`（その記事がフィード内に最後に見えた時刻）で判断する。マージは引き続き新しいほうの値を
残すが、差分が `cached_at` の変化を運ぶのは日付が変わったときだけである。そのため、自分ではそのフィードを更新しない
端末には、ほかの端末の `cached_at` が最大で約 1 日遅れて届くことがあり、保持期間の境目にあるスターなしの記事を、
以前より最大 1 日早く削除することがある——その削除は伝わる。スター付きの記事とフィードごとの最新 10 件はどの場合も
残り、収束にも影響しない。

## 差分同期以前の形式からの移行

差分同期以前の形式は、`/keryx.db.gz`（圧縮の導入前は `/keryx.db`）にある 1 つのデータベース全体である。この
バージョンを実行している端末が、ポインタは無いが `keryx.db.gz` を見つけたとき:

1. これまでどおり `keryx.db.gz` をマージし（検証、現行スキーマへの移行、`MergeSql`）、そのリビジョンを覚える。
   マージは記録の状態をそのままにして行う（`sync_merging` なし）: まだ参加していない端末では何も記録されず、手順 2 の
   全量送信がその行を運ぶ。すでに自分の世代へ送信した端末（ポインタを作る前に中断した以前の試行）では、変わった行が
   outbox に入り、差分として続く。
2. 参加する: 全量送信が最初のベースになり、ポインタを作る。ポインタがすでにあれば（ほかの端末が先に移行した）、
   通常の参加になる。
3. ダウンロードしたファイルを `keryx-YYYYMMDD-HHMMSS.db.gz.bak` としてアップロードする（`create`。その秒の名前が
   すでに使われていれば——中身が違うこともあるので——`keryx-YYYYMMDD-HHMMSS-1.db.gz.bak`、`-2`… と次の名前にする。それ以外の失敗では手順 4 の前に同期を終え、次の同期がやり直す）——手作業で戻すための一度きりの戻し口。
4. `keryx.db.gz` を、**手順 1 のリビジョンでのリビジョンチェック付きで**、`user_version` が 1000 の空の SQLite
   ファイルに置き換える。先に rename で退避することはしない: 確認してから rename するまでの間に古いビルドが書いた
   データが、マージされないまま退避されてしまうため。
   - リビジョン不一致 → ダウンロードして検証する。スタブ（ほかの端末が先に置いた）→ そのリビジョンを記録して
     完了。データベース全体（古いビルドが書いた）→ **記録を止めずに**（`sync_merging` なしで）マージするので、実際に
     変わった行はすべて outbox に入り、差分としてすべての端末に届く。そのうえで手順 4 をやり直す。
   - 成功 → そのリビジョンを `ks_legacy_stub_rev` として記録する。
5. スタブを読んだ古いビルドは、何かを書く前に `SchemaVersionException`（「アプリを更新してください」）を上げる:
   黙って乖離するのではなく、目に見える形で失敗する。（その `DatabaseMerger.merge` は、ローカルのデータベースを開く前に
   ダウンロードしたファイルの `user_version` を読む——どのプラットフォームでも `migrateCloudIfOlder`。）

スタブは名前や大きさではなく中身で見分ける: `user_version` が 1000 で、テーブルが無い。それ以外の新しいバージョンの
ファイル——テーブルを含む 1000 も——は、新しすぎるほかのクラウドファイルと同じく `SchemaVersionException` になる。
ポインタの無いスタブ（ポインタが手で消された場合など）は、差分同期以前のデータが無いことを意味する: そのリビジョンを
記録し、端末は最初の端末として始める。

**中断。** どの手順もクラウドの状態から決め直すので、どこでクラッシュしても後の同期で収束する: ポインタができる前なら、
次の同期はポインタが無く完全な `keryx.db.gz` があることを見てやり直す（マージは冪等。記録済みの送信は再開され、その
ポインタが作られる——「同期フロー」の手順 0 と手順 1）。ポインタができた後なら、旧ビルドの監視が、リビジョンが
`ks_legacy_stub_rev` でない完全な `keryx.db.gz` を見つけて手順 3〜4 を仕上げる。スタブのアップロード後、リビジョンの
記録前なら、監視がスタブをダウンロードして記録する。手順 3 の退避は、それを実行するほう——移行でも旧ビルドの監視でも——が
**この端末にスタブのリビジョンが記録されていない間**に作る: それまでの完全なデータベースは、差分同期以前の元のデータ
（中断した移行のもの、または別の端末がやりかけで残したもの）だからである。スタブを知った後に見つかった完全なデータベースは
古いビルドの後からの書き込みであり、マージはするが退避はしない。スタブの置き換えが `SYNC_MAX_RETRY` 回続けて
リビジョンチェックに負けた（ファイルが変わり続けた）ときは一時的な失敗とし、次の同期が続きを行う。

**使えない `keryx.db.gz`。** 検証に通らない `keryx.db.gz`（壊れている、またはマージできないデータベース全体）は、
移行でも旧ビルドの監視でも、同期のたびに `CloudDataIncompatibleException` で失敗させる。抜け出す手段は通知センターの
リセットである: ファイルを退避し、その場所にスタブを置く（「クラウドデータのリセット（退避）」を参照）。

**移行後に古いビルドが書いた場合。** Dropbox・OneDrive・Nextcloud では、そのリビジョンチェック付きのアップロードは
失敗し、再試行でスタブを読む。Google Drive ではリビジョンチェックが原子的でないので、スタブを上書きしうる。旧ビルドの
監視（「同期フロー」の手順 1）がリビジョンの変化に気づき、手順 4 とまったく同じように取り込んでから、スタブを置き直す。
Drive で古いビルドの上書きとスタブの置き直しが同時に起きると、古いビルドのその 1 回の書き込みが失われうる——
[known-issues.ja.md](known-issues.ja.md) の「Google Drive: アップロードが他端末のアップロードを気付かれずに上書きする
ことがある」と同じ原因である。

差分同期以前のデータベースは、現行スキーマがもう同期しない列を持つ: スキーマ 3 への移行は、その取得状態を一時ファイルの
中の `feed_fetch_state` にだけ移し（ローカルのデータベースには決して入れない）、タグとフォルダーを `2.sqm` と同じ手順で
作り直したうえで（フィールドごとのスタンプは `updated_at` で初期化、`UNIQUE(name)` を廃止、移行前の id を `v2_id` に
保持、子は退避・復帰）、名前から
導かれた id に振り直す（`IdGenerator.tagId` / `folderId`。ローカルの移行が走らせるのと同じ `AfterVersion(2)`
コールバック）。したがって現在の名前が一致すればその行はすでに移行済みの端末の行と同じ id で出会い、クラウドファイルが
移行される前に一方の端末でリネームされていた場合は異なる id を導くが、共通の `v2_id` によってマージで再統合されるので
別の同一性には分かれない。`articles.body_updated_at` を
`updated_at` で初期化する。その記事の `search_text` は、ほかのマージと同じく再計算する。

圧縮の導入前のビルド（`/keryx.db` だけを読む）はスタブの影響を受けず、それらについて文書化済みの一方向の乖離が
そのまま残る: このバージョンは `/keryx.db` を読みも書きもしない。旧ビルドの監視とこの移行は、v1.0.0 で削除する。

## クラウドデータのリセット（退避）

`SyncRepository.resetCloudData()` は、アプリが使えないクラウドデータからの回復手段である。何も削除しない: 端末は
**新しい世代**に参加し、ローカルの全状態をその世代のベースとしてアップロードし、リビジョンチェック付きでポインタを
置き換える（不一致——別の端末が先にリセットした——なら中止してポインタを読み直す）。前の世代のファイルは、読まれる
ことなく退避としてそのまま残る。ほかのすべての端末は次の同期で新しい世代を見て、自分の全量送信とともに再参加する
ので、ほかの端末にしかなかったデータも戻ってくる。

ポインタを置き換えた後、リセットは差分同期以前の `keryx.db.gz` に取りかかる。旧ビルドの監視が使えないもの（壊れている、
検証に通らないデータベース全体、読めないもの）が、同期のたびに失敗させ続けないようにするためである:

1. 無い → 何もしない。リビジョンが `ks_legacy_stub_rev` と同じ → 何もしない。
2. それ以外ならダウンロードする。ダウンロードの失敗（ファイルが消えた場合を除く）は、リセットを一時的な失敗にする——
   退避しないままファイルを置き換えることは決してない。
3. スタブ → そのリビジョンを `ks_legacy_stub_rev` として記録して完了。
4. それ以外 → 圧縮されたままの生のバイト列を `keryx-YYYYMMDD-HHMMSS.db.gz.bak` としてアップロードし（`create`。名前が
   使われていれば次の `-N` にし、それ以外の失敗ではリセットを失敗にする）、そのうえで `keryx.db.gz` を、**いまダウンロードした
   リビジョンでのリビジョンチェック付きで**スタブに置き換える。成功 → スタブのリビジョンを記録する。不一致（その間に
   ファイルが変わった）→ 手順 1 に戻る。これは最大 `SYNC_MAX_RETRY` 回で、超えるとリセットは一時的な失敗になる。

その中身は何もマージしない: リセットはクラウドのデータをこの端末の状態で置き換えるものであり、退避によってファイルは
手作業で戻せる。既存の `.bak` と有効なスタブには触れない。どの手順もクラウドの状態から決め直すので、どこでクラッシュ
しても収束する: スタブのアップロード前なら、旧ビルドの監視が次の同期をまだ失敗させ、次のリセットが仕上げる（別の名前で
もう一度退避する）。アップロード後、リビジョンの記録前なら、次の同期の旧ビルドの監視がスタブをダウンロードして記録する。
